# 青栏 Qinglan — 校园墙项目设计方案

> **项目名：青栏（Qinglan）** — 已定稿，后续不再变动
>
> 技术栈：后端 Java 21 + Spring Boot 3.x，前端 Vue 3 + TypeScript
> 定位：**校方可背书的校园信息基础设施**，而非民间匿名投稿账号
>
> 定名理由：取自「青青子衿」之"青"（学子）与"布告栏"之"栏"（官方信息发布）。
> 既区别于民间"表白墙"，又不被情感消费绑架定位。

---

## 一、合规底线（不可协商，先于功能）

| 依据 | 要求 | 本方案落实方式 |
| --- | --- | --- |
| 《互联网跟帖评论服务管理规定》[citation:16] | 后台实名、前台自愿；不得向未认证用户提供发帖/评论服务 | 学号或校园邮箱认证后方可发帖；前台显示随机代号 |
| 《网络暴力信息治理规定》（2024.8 施行）[citation:23] | 禁止以匿名投稿、隔空喊话名义创建版块/群组 | 取消"匿名投稿 + 运营者代发"模式，改为作者本人实名备案后发布 |
| 《网络安全法》第四十七条[citation:19] | 发现违法信息立即停传、消除、存证、报告 | 一键下架 + 全链路审计日志留存 6 个月 |
| 高校管理实践[citation:21][citation:25] | 未获学校授权不得运营、不得冒用校名 | 上线前完成学工处/宣传部备案，明确运营主体 |

**三条硬红线**：

1. 真实身份字段加密存储，运营管理员**无权限查看**（仅技术负责人依法配合调查时 decrypted）[citation:12]
2. 主帖**先审后发**，评论区先发后审 + 实时机审
3. 正文禁止出现姓名、学号、手机号、宿舍号、微信号——正则拦截 + 机审双重

## 二、用户与身份模型

```
游客 ──► 已认证学生 ──► 评议员 ──► 管理员
 (只读)    (可发帖)     (可投票)   (终裁+封禁)
```

- **认证方式**：校园邮箱验证码（主）+ 学号 + 校园卡照片人工复核（备），一人一校，认证后不可改绑
- **前台身份**：`匿名代号`（如"银杏树#3f2a"，按帖子随机生成，跨帖不可关联）+ 可选实名标识徽章
- **信用分**：初始 100，违规扣分，低于阈值限制发帖；严重失信列入黑名单[citation:16]

## 四、内容审核体系（核心）

**设计原则：不做图片内容识别。** 图片人物识别误报率高、成本重，且极易误伤正常的
失物招领（带人脸的校园卡）、活动合影。改为"发布轻审 + 事后举报下架"的事后治理。

```
用户提交
   │
   ├─ ① 发布前硬拦截（同步，毫秒级）
   │    敏感词库 · 隐私正则（仅拦截学号/身份证/银行卡）· 图片数量与大小
   │    ⚠ 不做图像识别，不做人脸检测
   │
   ├─ ② 轻机审（异步，秒级）
   │    文本内容安全 API · 重复帖检测 · 频率风控
   │
   ├─ ③ 放行即发布（默认通过）
   │    仅高置信违规文本才拦截，其余全部先发布
   │
   └─ ④ 事后治理（核心）
        用户举报 → 举报队列 → 管理员下架 / 驳回
        管理员主动巡查 → 下架
        下架后作者可申诉 → 复审
        同一帖累计 N 次有效举报 → 自动降为"仅自己可见"待处理
```

**举报驱动的下架流程**：

```
举报提交（选预设理由 + 可选补充说明）
   │
   ├─ 去重：同一用户对同一目标仅限 1 次（UNIQUE 约束）
   ├─ 聚合：按 target 聚合成"举报数"，进入队列排序
   │
   ├─ 管理员处置
   │    ├─ 下架（选违规类型）→ 通知作者 + 通知举报人 + 扣信用分
   │    ├─ 驳回（不成立）→ 通知举报人，举报数清零
   │    └─ 下架并封禁（严重/累犯）
   │
   └─ 申诉：作者 7 日内可申诉一次 → 换管理员复审 → 恢复或维持
```

**下架的三种力度**（别只有"删帖"这一档）：

| 动作 | 效果 | 适用场景 |
| --- | --- | --- |
| 隐藏联系方式 | 仅认证用户可见（详见 4.3） | 疑似诈骗、联系方式滥用 |
| 下架 | 作者可见，他人不可见，可申诉 | 一般违规、争议内容 |
| 下架并封禁 | 同上 + 限制发帖 N 天 | 人身攻击、累犯 |

**审核状态机**（用 Java 21 Sealed Interface 表达）：

```java
public sealed interface ReviewState
    permits Draft, Pending, Reviewing, Approved, Rejected, TakenDown {}

public record Pending(Instant submittedAt, RiskLevel risk) implements ReviewState {}
public record Rejected(String reasonCode, String explanation) implements ReviewState {}
public record TakenDown(String operatorId, String reason, Instant at) implements ReviewState {}
```

**审核工作台设计要点**（以举报队列为主视图）：

- 队列按举报数 + 等待时长排序，超时标红
- 一键操作：下架 / 驳回（选预设理由）/ 下架并封禁 / 隐藏联系方式
- 上下文面板：作者信用分、历史违规次数、举报人是否重复、同类帖举报数
- 所有操作写审计日志，不可删除
- 批量处置：同一作者的批量违规帖可一次处理

### 4.3 联系方式：放宽发布，收紧可见

**策略：允许带联系方式，但只给认证用户看。** 理由很直接——二手交易、失物招领、
拼车拼团没有联系方式根本跑不通，一刀切禁掉等于砍掉刚需；但把手机号裸奔给全网爬虫
是真实的泄露风险。

| 可见性 | 谁能看到联系方式 |
| --- | --- |
| 游客 / 未认证 | ❌ 不可见，显示"认证后可查看联系方式" |
| 已认证学生 | ✅ 可见（默认） |
| 被管理员标记 | ❌ 仅作者可见（隐藏联系方式处罚） |

**实现要点**：

- 正文不走正则硬拦截（原来拦截手机号的规则放宽），改为**渲染时脱敏**
- 后端返回帖子时按 viewer 身份决定 `contactVisible` 字段，前端按此渲染
- **关键**：脱敏必须在服务端做。只在前端用 `v-if` 隐藏，接口里还是会返回明文，
  抓个包就全漏了——这是最容易犯的错
- 联系方式字段独立存储（`post.contact`）而非混在正文里，便于统一控制与批量隐藏
- 查看联系方式写审计日志（谁看了谁的联系方式），被人恶意批量抓取时可追溯

```java
// 服务端按 viewer 决定返回内容，而非前端隐藏
public PostDTO toDTO(Post post, Viewer viewer) {
    boolean contactVisible = viewer.isAuthenticated()
        && post.getContactVisibility() != ContactVisibility.HIDDEN;
    return new PostDTO(
        post.getId(),
        post.getContent(),
        contactVisible ? post.getContact() : null,   // 未认证直接不返回
        contactVisible
    );
}
```

**高危时段加严：网暴帖集中在周末夜间、期中期末[citation:11]，该时段自动切换为全量人审。

## 五、公告与通知（双通道触达）

公告和通知必须分开设计。混在一起的结果是：校方的重要通告被几十条"谁赞了你"淹没，
强制触达失效——这是校园墙这类产品最容易做砸的细节。

| 维度 | 公告 Announcement | 通知 Notification |
| --- | --- | --- |
| 发布方 | 管理员 / 校方 | 系统自动生成 |
| 受众 | 全员（含未登录游客） | 个人 |
| 触达方式 | 访问站点主动弹窗 | 消息中心聚合 + 红点 |
| 强制性 | 强制阅读，必要时拦截操作 | 无强制 |
| 生命周期 | 有生效区间，过期转历史 | 长期保留 |
| 已读判定 | 服务端记录，跨设备同步 | 服务端记录 |

### 5.1 数据模型

```
announcement      id, title, content, level(URGENT/NORMAL/ACTIVITY),
                  status(DRAFT/PUBLISHED/REVOKED), start_at, end_at,
                  min_read_seconds, require_scroll_to_end, require_confirm,
                  supersedes_id, created_by, published_at, revoked_at

announcement_read id, announcement_id, user_id(NULL=游客), device_id,
                  read_at, read_duration_ms, confirmed
```

要点：
- 已读唯一键 `(announcement_id, user_id)`；游客退化为 `(announcement_id, device_id)`
- `read_duration_ms` 记录真实停留时长——这是"已强制阅读"的证据，后续争议时可调取
- `confirmed` 用于需勾选"我已了解"的紧急公告（如处分通报、安全通告）
- 撤回不删已读记录；更正走 `supersedes_id` 发新公告，不改写原文

### 5.2 强制阅读的判定条件（AND）

1. 倒计时满 N 秒（默认 5，紧急公告可配 10，`min_read_seconds` 控制）
2. 正文超过一屏时，需滚动到底部

双条件的理由：只等 5 秒，长公告会被"盲关"；只要求滚动，短公告会秒过。

### 5.3 前端实现要点

- 弹窗挂 `body`，遮罩点击不关闭，ESC 不关闭，浏览器返回不关闭
- 关闭按钮 `disabled` + 倒计时文案（"3s 后可关闭"）+ 进度条
- 焦点锁定（focus trap），Tab 在弹窗内循环，兼顾无障碍
- **不在打开时标记已读**——显示满时长后才调 read 接口，避免"打开即已读"的假强制

```
AnnouncementModal.vue   全局单例，挂在 App.vue
useAnnouncement.ts      composable：拉取 / 倒计时 / 滚动检测 / 标记已读
```

### 5.4 服务端兜底才是真强制

前端禁用只是体验层，用户禁用 JS 就能绕。真正的强制在服务端：

> 存在未读的 URGENT 公告时，`POST /api/posts` 返回
> `428 PRECONDITION_REQUIRED`，附带公告 ID，前端跳转弹窗。

即使绕过 UI，也发不了帖。是否启用此拦截由 `level=URGENT` 决定，普通公告不拦截，
避免过度打扰。

### 5.5 弹窗时机与排队

- 进入任意页面请求 `GET /api/announcements/pending`
- **一次只返回一条**：未读 + 生效中 + 优先级最高（`level` > `published_at desc`）
- 读完一条再拉下一条，直到为空——绝不堆叠弹窗
- 已在线用户通过 WebSocket 收到新公告推送，紧急公告立即弹

### 5.6 游客与跨设备

- 游客：cookie 下发 `device_id`，已读同时记本地与服务端
- 登录时合并：把该 `device_id` 的已读记录迁移到 `user_id`
- 换设备 / 清缓存：服务端记录兜底，不会重复弹

### 5.7 发布权限（强侵入能力要收紧）

强制弹窗是高侵入能力，滥用会直接毁掉产品体验：
- 仅 `super_admin` 可发布，普通管理员只能建草稿
- 发布需二次确认 + 写审计日志（谁、何时、发布了什么）
- 建议生产环境配公告频率上限（如每天 N 条）

### 5.8 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/admin/announcements` | 创建草稿 |
| POST | `/api/admin/announcements/{id}/publish` | 发布（二次确认） |
| POST | `/api/admin/announcements/{id}/revoke` | 撤回 |
| GET | `/api/announcements/pending` | 下一条未读公告 |
| POST | `/api/announcements/{id}/read` | 标记已读（带 duration_ms、confirmed） |
| GET | `/api/announcements` | 历史公告列表 |

## 六、技术架构

### 后端：Java 21 + Spring Boot 3.x

| 关注点 | 选型 | 说明 |
| --- | --- | --- |
| Web | Spring Boot 3.x | `spring.threads.virtual.enabled=true` 开启虚拟线程 |
| 安全 | Spring Security + JWT | 认证态与权限分离 |
| 持久 | Spring Data JPA + MySQL 8 | 或 MyBatis-Plus，按团队习惯 |
| 缓存/队列 | Redis | 限流、热点帖缓存、审核队列、代号生成 |
| 搜索 | MySQL 全文（一期）/ ES（二期） | 一期不引入 ES，降低复杂度 |
| 对象存储 | MinIO（自建）或 OSS | 图片上传，直传 + 回调校验 |
| 内容安全 | 第三方**文本** API + 本地词库 | 仅做文本，不做图像识别；需自建词库兜底（校外 API 不可用时） |
| 通知 | WebSocket / SSE | 审核结果与互动提醒 |

**虚拟线程用武之地**（真正 IO 密集的场景）：
- 内容安全 API 调用（批量文本审核）
- 图片转码与缩略图生成
- 举报聚合与队列排序计算
- WebSocket 广播与推送
- 举报聚合计算

**Java 21 特性落地**：`Record` 做 DTO、`Sealed` 做状态机、Pattern Matching 简化审核分支、`Optional` 避免空指针。

### 前端：Vue 3 + TypeScript

| 关注点 | 选型 |
| --- | --- |
| 框架 | Vue 3 + `<script setup lang="ts">` + Vite |
| 状态 | Pinia（用户态、草稿箱、未读通知） |
| 路由 | Vue Router 4 |
| 样式 | **UnoCSS** 原子化 CSS（`presetWind3`），语义色在 `uno.config.ts` 映射到 CSS 变量；主色 `#2E8B7A` |
| 学生端 UI | PC 为主、兼容移动端（PC 基准内容宽 1200px）；卡片流；**自研基础组件**（`components/base/`：Button/Input/FormField/Card…）；柔和配色 |
| 管理端 UI | **Element Plus + UnoCSS，仅支持 PC**（页面放 `views/admin/`，P3 起启用） |
| 请求 | 统一封装 + 拦截器（401 跳认证、错误 toast） |
| 测试 | Vitest + Vue Test Utils（组件）、Playwright（关键流程 E2E） |
| 全局弹窗 | `AnnouncementModal.vue` 单例挂 App.vue，配合 `useAnnouncement.ts` |

**发布页交互设计**（降低违规率的关键）：
- 输入框上方显示"禁止发布：姓名、学号、宿舍号、联系方式"动态提示
- 实时检测并高亮疑似违规片段，不给发布按钮
- 选话题后展示该话题的规则（如二手需留联系方式、失物需描述特征）

## 七、核心数据模型

```
user             id, student_id_enc, email_hash, credit_score, status, banned_until
post             id, author_id, topic_id, content, contact, contact_visibility,
                 status, report_count, risk_score,
                 anonymous_code, review_by, review_at, taken_down_at, created_at
post_image       id, post_id, url, thumbnail_url, sensitive_checked
comment          id, post_id, author_id, parent_id, content, status, created_at
topic            id, name, rules, requires_contact, enabled
like             id, target_type, target_id, user_id   (联合唯一)
report           id, target_type, target_id, reporter_id, reason_code, detail,
                 status, handled_by, handled_at, result
appeal           id, target_type, target_id, appellant_id, reason,
                 status, reviewed_by, reviewed_at, restored
review_log       id, target_type, target_id, action, operator_id, reason, created_at
notification     id, user_id, type, payload, read_at
announcement     id, title, content, level, status, start_at, end_at,
                 min_read_seconds, require_scroll_to_end, require_confirm,
                 supersedes_id, created_by, published_at, revoked_at
announcement_read id, announcement_id, user_id, device_id,
                  read_at, read_duration_ms, confirmed
```

要点：
- `anonymous_code` 按 `(post_id, author_id)` 派生，跨帖不可关联
- `report` 加 `UNIQUE(target_type, target_id, reporter_id)`，防同一人重复举报刷量
- `appeal` 独立于 `report`，记录作者申诉与复审结果；申诉仅限一次
- `review_log` 只增不改，留存 ≥ 6 个月
- `like` 用联合唯一索引而非先查后插

| GET | `/api/admin/review-queue` | 举报队列（按举报数 + 等待时长排序） |
| POST | `/api/admin/posts/{id}/take-down` | 下架（附违规类型，可加封禁） |
| POST | `/api/admin/reports/{id}/dismiss` | 举报不成立，驳回 |
| POST | `/api/appeals` | 作者申诉（每帖限一次） |
| POST | `/api/admin/posts/{id}/take-down` | 下架 + 审计 |

## 九、风控设计

| 风险 | 措施 |
| --- | --- |
| 刷帖/灌水 | Redis 令牌桶，按用户 + IP 双维度限流 |
| 偷拍挂人 / 人肉 | 不做图像识别；靠举报 + 管理员下架（目标：举报后 30 分钟内处置）；"找人打听"类话题默认隐藏联系方式 |
| 隐私泄露 | 仅硬拦截学号/身份证/银行卡；姓名、手机、微信改为**服务端按 viewer 脱敏**，认证用户可见 |
| 诈骗信息 | 二手/兼职话题保留联系方式但仅认证可见 + 交易风险提示浮层 + 举报直达队列 |
| 舆情升级 | 评论数/举报数突增自动降级为"仅审核可见"并告警管理员 |
| 老帖翻出 | 敏感争议帖 90 天后自动归档，需主动申请查看[citation:14] |
| 公告滥用 | 强制弹窗权限收至 super_admin，发布二次确认 + 频率上限 + 审计 |

## 十一、风险清单

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 未获校方授权即上线 | 强制下架、追责[citation:25] | 立项即启动备案，宁可延后上线 |
| 审核人力不足 | 违规内容扩散、承担责任[citation:19] | 学生评议员 + 高危时段全量人审 |
| 内容安全 API 单点 | 校外服务不可用时审核裸奔 | 本地词库兜底 + 降级为全量人审 |
| 身份数据泄露 | 侵犯隐私权，民事索赔[citation:8] | 加密存储、管理员不可见、最小权限 |
| 冷启动无内容 | 用户流失 | 与学生会/社团合作种子内容，先跑失物招领等刚需 |

## 十二、工程命名约定（青栏）

项目名已定稿为「青栏 / Qinglan」，以下命名全局统一，不再变动：

| 层面 | 命名 | 说明 |
| --- | --- | --- |

| 主色 | 青色系 `#2E8B7A` | 前端主题色 |

文档、接口路径、日志前缀、Docker 镜像名统一使用 `qinglan`。
