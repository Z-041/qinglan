# 青栏 Qinglan 内容审核规则

> 本文档随系统实现同步更新。本文档面向校方与内容审核人员，逐项说明平台的内容审核流程、举报与申诉机制、处置动作清单及留痕要求。文中所有状态、动作与阈值均与当前系统实现一致。

## 一、审核总原则

1. **主帖先审后发**：主帖必须经人工审核通过后才对作者以外的用户可见。
2. **评论先发后审**：评论发布即对其他用户可见，审核以事后处置为主（机审拦截 + 举报下架）。
3. **不做图片内容识别**：平台不对图片做机器识别或人脸检测，图片治理依靠"发布轻审 + 事后举报下架"。
4. **默认放行**：机审以高置信违规为拦截条件，除此之外内容一律先发布，靠举报与人工巡查事后治理，避免误伤正常内容。
5. **全程留痕**：所有下架、恢复、封禁、公告发布等管理动作写入只增不改不删的审计日志。

## 二、发布前硬拦截（同步，毫秒级）

用户提交内容时，系统在落库前同步执行以下检查，命中即拒绝发布，不进入审核队列：

| 检查项 | 规则 |
| --- | --- |
| 敏感词 | 内置本地敏感词库（一行一词，随时可扩充），命中即拒绝 |
| 隐私信息 | 内置正则识别身份证号、银行卡号，命中即拒绝 |
| 图片数量与大小 | 单帖图片不超过 9 张，单张不超过 5 MB，超限直接拒绝 |
| 发布门槛 | 账号处于封禁或黑名单状态、或信用分低于 60 分时，拒绝发布 |
| 上传频率 | 单用户每分钟最多 30 次上传，超限拒绝，防止刷爆存储 |

正文与联系方式字段**分别**经过敏感词与隐私信息检查，联系方式不会被漏检。

> 说明：系统当前硬拦截的隐私信息为身份证号与银行卡号。姓名、手机号、宿舍号、微信号等不在此硬拦截范围内，而是通过"联系方式只对认证用户可见 + 服务端按访问者脱敏"的方式保护。

## 三、主帖审核流程

主帖使用状态机管理，禁止跳态，非法迁移会被系统直接拒绝。

```
Draft（草稿）
   │ 作者提交
   ▼
Pending（待审）
   │ 管理员认领
   ▼
Reviewing（审核中）
   ├──► Approved（通过，对所有人可见）
   └──► Rejected（驳回，附理由，仅作者可见）
          │（驳回后作者可修改再提交）
Approved ──► TakenDown（下架，作者可见、他人不可见，可申诉）
TakenDown ──► Approved（申诉通过 / 管理员恢复）
```

- 帖子提交后进入**待审**，在审核通过前，除作者本人外任何用户（含游客）都无法看到该帖子。
- 审核通过后帖子对所有人可见。
- 驳回时管理员须填写理由，理由对作者可见，作者据此修改后再提交。
- 已通过（Approved）的帖子可直接被下架（TakenDown），下架后仅作者本人可见。
- 下架状态只能通过申诉复审通过或管理员恢复可回到"通过"，不存在"下架直接回到待审"的跳态路径。

## 四、举报机制

### 4.1 举报的受理

- 举报人须为已认证且账号可用的用户，游客与未认证用户不能举报；
- 可举报的目标为**帖子**与**评论**；
- 举报须选择预设违规类型：广告与推广、色情低俗、辱骂与人身攻击、泄露他人隐私、诈骗与欺诈、违法违规、与话题无关、其他（选"其他"须补充说明）；
- 用户不能举报自己的内容；
- 用户不能举报对自己不可见的内容（待审、已下架且非本人）——此类目标按"不存在"处理，不泄露其存在性。

### 4.2 去重（数据库唯一约束保证）

同一用户对同一目标仅可举报一次。系统在写入前预检并在数据库层以唯一约束兜底：

- 重复举报返回"已举报过"的明确错误，**不会静默忽略**；
- 并发提交时唯一约束只会放行一条，后到的同样得到"已举报过"的提示。

### 4.3 聚合与自动下架

- 举报按目标聚合为"待处理举报数"，进入审核队列；
- 队列按**待处理举报数**为主要排序键，结合等待时长排序；
- 帖子待处理举报数达到 **3 条**时，系统**自动下架该帖**并转入人工复核，同时通知作者；
- 自动下架**不结案**这些举报——举报保持待处理状态，帖子留在队列里等待人工确认；
- 自动下架同样写入审计日志，操作人记为系统（非人工点选）。

## 五、处置动作清单

以下动作在管理端审核工作台均可执行，每一项都会写入审计日志：

| 动作 | 适用场景 | 对内容的实际效果 |
| --- | --- | --- |
| 通过 | 待审 / 审核中的帖子 | 帖子对所有人可见 |
| 驳回 | 审核中的帖子 | 帖子不对他人可见，向作者显示理由 |
| 下架 | 已通过的帖子 | 帖子仅作者可见、他人不可见，作者可申诉；同时结案该帖全部待处理举报并清零举报数；可同时选择封禁作者 N 天（"下架并封禁"） |
| 恢复 | 已下架的帖子 | 帖子重新对所有人可见（申诉通过走同一路径） |
| 隐藏联系方式 | 疑似诈骗、联系方式滥用 | 联系方式仅作者本人可见，帖子本身仍可见 |
| 撤销隐藏 | 误判纠正 | 联系方式恢复对认证用户可见 |
| 移除评论 | 违规评论 | 评论被移除，并结案该评论的全部待处理举报 |
| 驳回举报 | 内容未违规 | 该目标全部待处理举报结案、举报数清零，内容不受影响 |
| 维持下架 | 确认举报成立且内容已在下架态 | 结案全部待处理举报并清零举报数，内容保持下架 |

**下架三种力度**说明：

1. **隐藏联系方式**：适用于疑似诈骗、联系方式滥用等情形，内容仍可讨论；
2. **下架**：适用于一般违规、争议内容，作者可见、可申诉；
3. **下架并封禁**：适用于人身攻击、累犯等，在下架的同时限制作者账号 N 天。

**通知**：下架通知作者（附理由）；举报被处理（维持下架或驳回）后，逐条通知各自的举报人。

## 六、申诉与复审

- **受理范围**：**仅被下架（TakenDown）的帖子**可以申诉。其余处置没有对应的回退路径，不受理申诉。
- **申诉人**：必须是帖子作者本人。
- **时限**：自下架时刻起 **7 日**内，超期不再受理。
- **次数**：**每帖限一次**，重复申诉被明确拒绝（数据库唯一约束兜底）。
- **复审人**：由**另一位管理员**复审，**原处置人不得复审自己处置过的内容**。这是硬性规则，复审时会校验原处置人身份并在冲突时拒绝。
- **复审结果**：申诉通过则恢复帖子可见并通知作者；申诉不通过则维持原判并通知作者。复审决定本身与内容状态变更分别写入审计日志。

## 七、留痕要求

- 审计日志（`review_log`）**只增不改不删**，系统不提供任何修改或删除审计记录的接口；
- 所有下架、恢复、封禁、解封、信用分调整、隐藏/撤销隐藏联系方式、移除评论、举报结案、公告创建/发布/撤回、查看联系方式等动作均落审计；
- 审计记录包含目标类型、目标 ID、动作、操作人、理由与时间；
- **系统自动处置**（如举报数达阈值自动下架）的操作为系统哨兵值，与人工操作可区分；
- 审计日志保留期不少于 6 个月，满足违法信息处置的存证要求。

## 八、处置时限

- 管理员在审核队列中按举报数（降序）与等待时长（升序）处理；**首条举报提交超过 24 小时**仍未处置的条目，在管理端以高亮标记提示，便于优先处理；
- 平台对举报的处置目标为**举报提交后 30 分钟内完成首次处置**。该目标依赖审核人力值守，运营方须保证在工作时段内有审核人员在岗。

## 九、图片与多媒体

- 平台不做图像内容识别，也不做人脸检测。原因是识别误报率高、成本重，且极易误伤带人脸的校园卡、活动合影等正常内容；
- 图片治理采用事后模式：发布时仅做数量与大小限制，发布后依靠举报与人工巡查下架；
- 图片存储于对象存储，不落应用服务器本地磁盘；图片地址只接受本站上传产生的路径，外部链接无法注入。
