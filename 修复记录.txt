R-56 前端组件整合第五批（5C 波）：学生端弹层焦点陷阱 + 点赞可访问名 + 图片并入收口
--------------------------------------------------------------------------------
[2026-10-11]  类型：组件/接口优化  状态：已交付；学生端 lint/typecheck/vitest/build 真跑全绿
来源：第五批 5C，收尾波。

一、交付
  1. useFocusTrap.ts（web/composables）：弹层焦点陷阱——激活时收焦点、Tab / Shift + Tab 在容器内
     循环、失活时把焦点还给打开前的元素；无可聚焦元素（强读弹窗倒计时中关闭按钮 disabled）时聚焦
     容器自身。ESC 语义各弹层不同，仍由调用方自理，本组合不拦截。
     - AnnouncementModal 原来自写了一套（约 50 行），改为复用；ModalShell 原来只有「收焦点」、
     无 trap，接入后举报弹窗 / 删除确认也获得真正的键盘可用性（此前 Tab 会跑到背景页面）。
  2. ModalShell：`closeOnBackdrop` / `closeOnEsc` 合成 `dismissible`——两个 prop 在所有真实调用点
     恒等共变（都是「提交在途则不可关」），合成后不会出现「能点遮罩关、ESC 却关不掉」这类自相矛盾。
     ConfirmDialog / ReportDialog 随之改传一个 prop；ModalShell.spec 的两条「分别受控」用例合并为
     「默认可关 / dismissible=false 时遮罩与 ESC 都不关」。
  3. LikeButton：可访问名由 `liked` 派生（「点赞 / 取消点赞」），可选 `subject`（评论者代号）拼成
     「点赞 梧桐#3 的评论」；`label` 保留为覆盖项。PostCard / PostDetailCard 删掉各自复制的
     `liked ? '取消点赞' : '点赞'` 三元，CommentItem 改传 `:subject`。
  4. useImageUpload 增 `addTo`：把「上传 + 并入当时列表 + 按上限截断」收进 composable，「最多 9 张」
     这条规则不再在视图里各写一份 slice。**await 回来后再读一次目标列表**再合并——在 await 前取快照
     会让上传期间删掉的图复活，PublishView 的既有 spec 正盯着这点。
  5. PostImageGrid：variant / 图片数派生的两处样式提为 computed，不在 v-for 的每张图上重复求值。
  6. usePostDraft：去掉 watch 的 `deep`——四个源都是 ref，且 images 恒为整体替换（ImagePicker /
     发布页均替换 .value），deep 只是徒增嵌套比对。零行为变化。

二、评估后不做（逐条给理由）
  1. **useHistoryGuard 不抽**：返回键守卫只有 AnnouncementModal 一个消费者，抽出不消除重复，
     按「不为一次性操作造抽象」不划算（与其焦点陷阱不同，焦点陷阱有两处消费者）。
  2. **usePostDraft 防抖不做**：正文上限 2000 字，每键一次 JSON 序列化 + localStorage 写入实测开销
     可忽略；加防抖会引入「防抖窗口内关闭标签页丢最后几字」的窗口，并要改动 3 条既有 spec 的时序，
     收益不抵（本波只做零风险的去掉 deep）。
  3. **useAnnouncement 收窄导出不做**：它导出的 17 项里确有仅内部 / 测试使用的字段，但该 composable
     是复杂的有状态单例，收窄要同步改其 spec 的多条用例，属「整理导出面」而非缺陷；留作后续。
  4. **PublishView 的草稿恢复编排不下沉**：它由「回填字段 → 换图 → 按 missing 提示 → 失败保留原值」
     四步组成，且与 usePostDraft / useImageUpload 两个已有 composable 协同，再包一层只是转发。

验证（真跑，全绿）
- pnpm lint / typecheck：学生端通过。
- vitest：qinglan-web 36 文件 208 例全绿（较 5B 落点 206 例 +2，为 LikeButton 新增的两条派生断言；
  ModalShell.spec 的关闭语义用例随 prop 合并同步，PublishView.spec「上传期间删图不复活」原样通过）。
- pnpm build：学生端产物成功。
- 过程修正：`addTo` 初版签名收 `string[]`（调用前取快照），导致 PublishView 的「上传期间删图不复活」
  用例红；改为收 `Ref<string[]>`、在 await 后再读一次列表——正是该 spec 早已覆盖的语义。

R-55 前端组件整合第五批（5B 波）：管理端 composable 归一（轮询 / 筛选游标 / 确认框）
--------------------------------------------------------------------------------
[2026-10-11]  类型：composable 归一  状态：已交付；管理端 lint/typecheck/vitest/build 真跑全绿
来源：第五批 5B。5C（学生端）另开。

一、交付（3 件，均带 spec）
  1. useVisibilityPolling.ts（原语）：可见性感知的定时轮询——只在页面可见时按间隔执行，切后台暂停、
     切回恢复，带防重入与生命周期自动启停。useQueuePolling 与 useTodoCounts 此前各复制了一整套
     脚手架（计时器 + 可见性 + 防重入 + onMounted/onScopeDispose），仅「探针逻辑」与「start 时是否
     先跑一次」不同（队列 false、待办计数 true，用 immediate 选项表达）。
  2. useFilteredCursorList.ts：在 shared/useCursorList 之上叠加「筛选已改但未重查」的记账——
     续页闸门（加载更多）+ 探针用「列表实际对应的筛选」（effectiveFilters）。举报队列（手写
     snapshot + 逐字段 equals）与用户管理（JSON 串）原先各写一份，统一到 JSON 串口径。
     关键点：快照在**发起请求时**捕获，onApplied 用请求时的快照记账——避免请求在途时用户又改筛选
     被误记为「已应用」（原 useReviewQueue 手写实现即如此，迁移后行为不变）。
  3. useConfirm.ts：ElMessageBox.confirm 的统一封装，确认返回 true、取消 / 关闭返回 false（不抛）。
     收口 AnnouncementManageView 里两处逐字重复的「发布 / 撤回」确认。

二、评估后不做（2 项）
  1. **三视图下沉 composable（PermissionManageView / AuditLogView / AnnouncementManageView）不做**：
     这三处逻辑都只有单一消费者、与别处无重复，抽出来只是把代码从视图搬进新文件，不消除任何重复，
     按 AGENTS「不为一次性操作造抽象」的口径收益不抵（其中真正的纯逻辑——委员会规则——早已在
     rolePolicy.ts）。视图本身也不长（124–171 行）。
  2. **ReviewActionBar 的权限 / 可用动作判定上移不做**：`usePermissions` 是模块级 UI 单例，**不是
     Pinia 业务 store**，故未触 AGENTS「展示组件不得直取 store」这条硬规则；而把判定上移会改动组件
     公开 API（新增 actions prop），并使 ReviewActionBar.spec 里 8 条「按状态给哪些动作」的断言失去
     被测对象（需新建 reviewActionSet.spec 承接），改动面与收益不匹配；组件内注释已说明其与快捷键
     共用同一份 permission 口径的用意。

R-54 前端组件整合第五批（5A 波）：管理端契约与性能收口
--------------------------------------------------------------------------------
[2026-10-11]  类型：组件/接口优化  状态：已交付；管理端 lint/typecheck/vitest/build 真跑全绿
来源：第五批（用户选定「三波全做」）。四批之后深度复扫发现本批不再有「逐字重复」，剩余是
API 设计与实现层面的优化；5A 收口管理端的契约与性能。5B / 5C 另开。

一、交付（4 项）
  1. EChart 去掉 `deep: true`：option 来自视图 computed，每次重算都是新引用，浅监听即可触发；
     deep 会递归遍历整棵 EChartsOption（含 series / data），纯属浪费。零行为变化。
  2. 表格 emit 名统一 `handle` → `select`（QueueTable / PendingPostTable + 两个消费视图 +
     各自 spec）：与周边表格的 `review` / `publish` / `ban` 等动词口径一致；`select` 也更准
     （点击是「选中该行到侧栏处置」）。

     - useReviewContext.reload（仅 spec 引用，生产视图靠 selectActive→open 重开面板）；连带删其 spec 用例。
     - useRowKeyboardNav 的 blur（全仓零引用）、moveUp / moveDown（仅内部 handleArrowKeys 用，
       不必外露）；内部函数保留，仅从 return 收窄。

     datetime-local → ISO(UTC)；其中审计日志那版不 trim 且非法日期会 **抛 RangeError**，统一为

    原列为本波项，复核后**不做**：其「不传即无刷新按钮」是被测试的**有意能力**
    （PageHeader.spec.ts:12-15、40-46 两例），显式化要么删掉该能力、要么新增一个 prop；当前
    prop 注释已写明语义，改动收益不抵。留待真正需要「无刷新按钮页头」时一并设计。

三、行内提交态（小修）

R-39 私有图片在浏览器中取不到（<img> 不带令牌）：按 viewer 签发短时签名 URL
--------------------------------------------------------------------------------
[2026-10-09]  类型：设计疏漏修正  状态：已交付；后端真跑验证，浏览器真实取图与真实对象存储未实测
来源：用户反馈——刚上线的图片可见性改造（T-27①，/uploads/** 由应用校验可见性）在浏览器里失效。

现象
  - 发帖页图片预览 404 破图（上传后还没发帖的「未绑定上传」）。
  - 作者打开自己「待审 / 已下架」的帖子，配图 404 破图。
  - 而同一地址带上作者令牌用 curl 取却 200 —— 差别只在「浏览器 <img> 不发 Authorization」。

根因（设计疏漏，不是实现 bug）
  - T-27① 把 /uploads/** 从静态资源改成受控端点、按 accessor 判可见，方向正确；但它默认「请求方
    携身份」。浏览器 <img> 请求**不携带 Bearer 令牌**，被服务端当成游客——未绑定上传只对上传者可见、
    待审/下架帖图只对作者可见，于是作者本人也被判成无权，404。前端加不了这个头（<img> 没有该能力）。

处理（已与用户确认的方案：服务端下发 DTO 时按 viewer 决定 URL，前端零改动）
  1 签名 URL 形态（StorageUrl 为唯一出处，签名的拼装/解析都在它附近）：
      /uploads/YYYY/MM/<hex>.<ext>?exp=<epochSeconds>&sig=<base64url(HMAC-SHA256(objectKey + ":" + exp, secret))>
  2 校验（在图片下发端点）：带 exp+sig → 常量时间比较（MessageDigest.isEqual）+ 未过期 + 不超过
    「now + 有效期上限」→ 放行，**不依赖 viewer 身份**；非法/过期/超上限 → 与「不存在」同码同状态
    404（不给攻击者区分信号）；无签名（或只带其一）→ 走原有身份判定路径，行为不变。
  3 密钥：新增 qinglan.storage.image-signing-secret；留空回落 qinglan.jwt.secret（**权宜**，仅本地/
    测试便利）。prod 启动守卫追加一条：该密钥必须显式配置、不得依赖回落。日志与错误信息不打印密钥
    或完整签名。
  4 装配侧（按 viewer 签发，收敛在 ImageUrlAssembler 一处）：所属帖子 APPROVED（对所有人公开）→
    原 URL（保持干净、可缓存、可被浏览器缓存）；其余（PENDING/REJECTED/TAKEN_DOWN + 未绑定上传）→
    签名 URL。落点：帖子详情、我的帖子、上传接口返回。
  5 批量换取端点 POST /api/uploads/image-urls（需登录）：入参一组 URL，出参每项 {url, available,
    usableUrl}；只对本人有权访问的对象签发，无权者明确 available=false 且 usableUrl=null，**绝不签发**。
  6 草稿场景：草稿只存原 URL（保存时剥离签名查询串）；恢复时前端调批量端点换取当前可用地址，
    换取不到的剔除并提示「需重新上传」，不静默破图。
  7 文档：application.example.yml、.env.example（密钥只走环境变量）、deploy/README.md（签名机制、
    有效期、守卫表）。

为什么选签名 URL，而不是「前端用 fetch 带令牌取 blob 再喂给 <img>」
  - fetch+blob 要把每个 <img> 换成一个带令牌的请求 + URL.createObjectURL + 手动 revoke，改动面覆盖
    所有展示图片的组件；且拿不到 HTTP 缓存/断点续传，列表页每张图都重复下载。
  - 签名 URL 对前端是普通 <img src>，缓存、CSP（img-src 'self'）、懒加载全部照旧；后端一处 helper 即可。
  - 签名校验不依赖身份，绕开了「<img> 无法带令牌」这个根本约束。

签名带来的小泄漏面与缓解（诚实登记）
  - 签名 URL 一旦被复制/转发，在过期前「谁拿到谁能看」。缓解：exp 取短（默认 10 分钟）+ 硬上限 1 小时
    （配置更大值会被收敛），并拒绝远期 exp；签名只绑定单个 objectKey，不能跨对象复用。
  - 密钥单一：泄露即可为任意对象签发。缓解：与 JWT 密钥分离（生产强制独立配置），可单独轮换（轮换只
    使已签发链接失效，影响面小于 JWT）；不进日志。
  - 未做：按 IP/UA 绑定签名、签名吊销列表（当前短 exp + 单一密钥已覆盖已知威胁，是否加强由部署方定）。

验证（真跑）
  - 后端 ./mvnw test：589 用例、0 失败、0 错误、6 跳过。新增 17 条：ImageUrlSignerTest（9）、
    ImageSignedUrlIntegrationTest（7）、ProdEnvironmentGuardTest 签名密钥 1 条。
  - 覆盖：正确签名游客可取；篡改/过期/超上限 → 404；缺参数按无签名走身份路径；APPROVED 图 URL
    不带签名且游客 200；待审/下架帖作者视角带签名且不带令牌可取；下架后旧干净 URL 立即 404
    （T-27① 不失效）；上传返回立即可用；批量端点本人签发、他人私有图不签发、公开图返回原 URL、
    需登录（401）；TTL 硬上限收敛；密钥回落。
  - 前端三包 lint/typecheck/test/build 全绿（见本轮交付输出）。
  - 未验证（须写明）：真实浏览器 <img> 取图（无浏览器环境）、真实对象存储（S3 兼容）端到端表现、

    浏览器看 PENDING 帖原图同样会 404 —— 与 R-39 同源，属遗留缺口，建议下一轮按同一 helper 处理。
  - 草稿恢复的边界：换取失败的请求（网络）只保留原地址、不提示（错误由拦截器 toast）；被孤儿回收
    任务清理的上传会 unavailable，需重新上传。
  - 回落配置键：任务说明里写作 qinglan.auth.jwt.secret，实际配置键是 qinglan.jwt.secret
    （JwtProperties prefix=qinglan.jwt），实现按**实际**键回落。

R-31 全链路审查：补齐 2 处功能缺陷、2 处安全缺口、5 处健壮性与索引缺口
--------------------------------------------------------------------------------
[2026-10-08]  类型：审查 + 缺陷修复  状态：已交付
来源：用户要求「审查所有链路看看有没有缺陷或漏洞，把它们补全」。
方法：四个只读子代理并行铺开（内容与审核链路 / 认证与安全 / 前端三包 / 数据层与待办），
      每条候选**都由我回源码复核后才动手**，不采信未复现的结论。结果是 9 条确认项。

一、功能缺陷（P1）
  F1 428 拦截范围错了：`PostService.create` 调 `announcementService.findPending(authorId, null)`，
     而该方法**不按级别过滤**（只按 status/生效窗口，级别仅用于排序）。于是**任意一条未读普通
     公告都会挡住全站发帖**，与设计方案 5.4「是否启用此拦截由 level=URGENT 决定，普通公告不
     拦截」相反（不变量 #6 也只写「未读紧急公告」；ErrorCode 文案就是「存在未读的紧急公告」）。
     修：仓储 `findPending` 增加 `levels` 入参；`AnnouncementService` 拆成 `findPending`（弹窗，
     全级别）与 `findPendingUrgent`（仅发帖 gate）；PostService 改调后者。
     测试：AnnouncementServiceTest 加「gate 只查 URGENT」、AnnouncementRepositoryTest 加 2 例
     （只查 URGENT 时普通公告被排除 / 只有普通公告未读时 gate 为空而弹窗口径仍取得到）、
     PostServiceTest 加「只问紧急口径」的合同断言。

  F2 「恢复可见」不清举报计数，恢复后一次新举报就再次自动下架：
     `restore` 只改状态；而自动降级路径（举报数达阈值）**刻意把举报留在 PENDING 且不降计数**
     （ReportService 注释写明）。于是 3 人举报 → 自动下架 → 管理员恢复 → 计数仍是 3，任何一人
     再举报一次就再次触发 `autoTakeDownIfNeeded`，「恢复」形同虚设；队列里还会长期挂着一条
     targetStatus=APPROVED 的行。`restore` 的原注释假设「举报早在前置处置时已结案」，该前提
     对手工下架路径成立、对自动降级路径不成立。
     修：restore 顺带把该帖待处理举报结案为 DISMISSED 并按条数原子回退 report_count（空则不减、
     不写多余审计），同时反馈举报人——与 takeDown/upholdReports/dismissReports 同一口径。
     手工下架路径本就是空操作，行为不变。申诉通过走 restore，同样受益。
     测试：ReviewServiceTest 加 2 例（结案并回退计数 / 无待处理举报时不动计数）。

二、安全缺口（P1）
  F3 管理端写入口不复查账号状态：令牌是无状态的、角色在签发时固定，而业务模块
     （发帖/评论/举报/申诉/上传）都在写入口调 `requireUsableById`（UserService 注释明确要求
     「每个写入口都要重新校验一次」），**管理端点没有这一步**——被封禁的管理员在令牌剩余有效期
     （默认 2h）内仍能封禁他人、下架内容、发公告，权限撤回有一个最长 2 小时的窗口。
     修：新增 `AdminWriteGuardFilter`（auth/security，紧跟认证过滤器）——`/api/admin/**` 的非
     GET/HEAD/OPTIONS 请求先复查操作人是否可用，不可用即走 SecurityConfig 既有的
     AccessDeniedHandler 返回统一的 403 JSON（过滤器里抛 BizException 不会被 @ControllerAdvice
     接住，故不抛异常；具体原因不回显）。只拦写：与「封禁学生仍可浏览」同口径（经验 #13）。
     不新增跨模块方向（auth → user 早已在白名单内）。
     测试：AdminWriteGuardFilterTest 5 例（封禁拒绝、可用放行、读放行、未认证交给授权规则、
     非管理前缀不管）。

  F4 匿名「标记已读」接口的限流维度可被客户端伪造：限流主体是 `deviceId`，而 deviceId 完全由
     请求方提供（只校验字符格式），轮换 deviceId 即每次独立配额，可对同一条公告无限插入
     announcement_read 行。属资源放大，不涉及机密或完整性。**未修**：真正的修法要引入不受客户端

R-28 前后台会话模型澄清与会话语义修复（单会话约定 + 退出跳转 + 角色口径统一）
--------------------------------------------------------------------------------
[2026-10-07]  类型：缺陷修复 + 约定澄清  状态：已交付
来源：用户指出「前端没区分学生端与管理端：后台登录与前台上登录是一样的，前台退出后后台也同时
      退出」。经核查属实，但**根因不是漏写隔离**，而是从设计上就是「一份令牌 + 一个 store」。
      先把事实与取舍摆清，由用户在两个产品决策上拍板（AGENTS.md 第十一章第 4 条），再动手。

核查结论（前端「前后台不分」的原因）

  1 令牌只有一份：api/http.ts 的 TOKEN_STORAGE_KEY = 'qinglan.access-token' 与模块级
    memoryToken，所有请求共用
  2 用户态只有一份：stores/user.ts 的 accessToken / profile
  3 两个登录页写的是同一个 store：useAuth 的 verify / bind 都调 userStore.setAccessToken()，
    不看区域
  4 两处退出也调同一个 signOut()：App.vue（学生端）与 AdminLayout.vue（管理端）
  5 后端同样只有一份身份：JWT 里就是 userId + role，没有「前台会话/后台会话」的概念

  故「前台登录＝后台登录」「前台退出＝后台退出」是该结构的必然结果，不是实现缺陷。

  - 会话模型：**保持单会话**，不拆双令牌；补严语义

  1 前台退出不跳转（真缺陷，本轮核心）。App.vue 的 sign-out 只调 userStore.signOut()、
    不做导航，而路由守卫只在**导航时**运行——若当时在 /profile（requiresAuth），档案已清空、

    表单上。管理端退出是有 router.replace('admin-login') 的，两边行为不一致。
    处理：App.vue 增 handleSignOut()——清登录态后，当前路由 meta.requiresAuth 为真则回首页；
    游客本就能浏览的页面（首页、详情）留在原地、自动切游客态，不打断浏览

  2 管理员从前台登录无任何身份提示。前台登录页不校验角色，管理员从前台登录后 /admin 守卫

    处理：LoginView 的 afterAuthenticated() 中，若当前角色属管理员则提示「当前为管理员账号，
    可访问管理后台」；**刻意不拒绝**（管理员同时是本站认证用户，挡在社区外与其身份冲突）

  3 角色准入口径此前有三份。router/index.ts 与 AdminLoginView.vue 各写一份 ADMIN_ROLES，
    本轮又要在 LoginView 判断一次，属第三处重复；三份一旦漂移就会出现「前端放行、后端 403」。
    处理：抽取到 types/user.ts 的 ADMIN_ROLES / isAdminRole()（唯一来源），三处改为引用

  4 约定写入 AGENTS.md 第七章：一个浏览器 = 一个账号 = 一份会话，并派生三条硬约束
    （退出必须跳转、管理员可从任一登录页进入但须提示身份、角色口径只有一份）；
    同时写明「若将来要同浏览器双身份登录，属架构变更（需双令牌 + 按区域切 Authorization），
    先提 issue」——把这次的取舍固化成规则，避免后来者就地乱改

    ——404/410 走 fatal 直接跳过（已撤回的公告不再是「生效中」，放行不影响强制）；网络/5xx/429

     处理：倒计时改成按「目标时刻 − 现在」计算，与 durationMs 同源
  11 openFromPrecondition 会覆盖正在读的公告。428 触发时若已有一条在展示，会重置展示时刻与

R-23 P2 审核体系复审（6 处缺陷：幂等 / 终态 / 可逆性 / 游标 / 写入口 / 并发）
--------------------------------------------------------------------------------
[2026-10-06]  类型：缺陷修复（P2 复审）  状态：已交付
来源：对 P2 审核体系做代码审查（两个子代理交叉验证），6 条全部成立、无一误报；
      经用户批准「全部修复」。

现象（6 条）
  1 ReviewService.restore 缺幂等：帖子已是 Approved（他人已手工恢复）时，复审通过走
    Approved → Approved，状态机判为非法迁移抛 ILLEGAL_REVIEW_TRANSITION，整个复审事务
    回滚，连申诉状态也一并退回。
  2 自动降级后举报无合法结案入口：举报数达阈值自动下架时，举报刻意保持 PENDING 以留在队列，
    但管理员认同下架时既不能走 takeDown（TakenDown → TakenDown 非法），走 dismissReports 又
    把它记成「内容不违规」（DISMISSED），与事实矛盾。举报永远挂在队列里。
  3 「隐藏联系方式」不可逆：Post.showContact() 是死代码，没有任何处置能恢复可见性，一次
    误判即永久生效。
  4 审核队列游标缺 target_type：target_id 只在各自类型内唯一（帖子 #7 与评论 #7 撞号），
    若两者举报数与首报时间并列，仅凭 target_id 无法区分，翻页会漏行或重复。
  5 AppealService.submit 未校验账号可用：与 ReportService.report 口径不一致，被封禁账号
    仍可提交申诉。
  6 并发重复申诉抛 DataIntegrityViolationException：uk_appeal_target 挡住后落到全局
    catch-all 500，而非约定的 409。

根因
  1 状态机 APPROVED 的合法后继只有 TAKEN_DOWN（不含自身），restore 未对「已经是目标态」做
    短路，把「无需迁移」当成了「非法迁移」。
  2 自动降级刻意保留 PENDING，却只补了下架动作，没补「人工确认举报成立」这个终态动作。
  3 hideContact 落了处置但漏了撤销路径（同类处置 restore 有、showContact 无）。
  4 队列排序键当时只考虑单类型，未意识到 target_id 跨类型会撞号。
  5/6 申诉写入口比举报写入口少做了一步账号校验与一次唯一键冲突映射。

处理
  A restore 幂等短路（ReviewService.restore）：进方法先判 post.status == APPROVED，是则记
    日志直接返回，不迁移、不写审计。消除「作者申诉后、复审前他人已手工恢复」的窗口，避免
    复审因非法迁移整体回滚。
  B 新增「维持下架」处置（ReviewService.upholdReports + 端点
    POST /api/admin/posts/{postId}/uphold-reports + 审计码 REPORT_UPHOLD）：前置校验帖子必须
    处于 TAKEN_DOWN（否则抛 ILLEGAL_REVIEW_TRANSITION），取该帖全部 PENDING 举报置 UPHELD，
    按结案条数原子回退 report_count（不直接写 0，避免覆盖并发新增）；无待处理举报抛
    REPORT_NOT_FOUND。只结案举报、不动内容状态。
  C 新增「恢复联系方式可见」处置（ReviewService.showContact + 端点
    POST /api/admin/posts/{postId}/show-contact + 审计码 POST_SHOW_CONTACT）：调
    Post.showContact() 把 contactVisibility 改回 VISIBLE，写审计。补上隐藏的撤销路径。
  D 队列游标纳入目标类型（ReportRepository.findQueueAggregates + ReviewQueueService）：排序键
    与 having 增加第四段「目标类型序」，case 表达式 POST=0 / COMMENT=1；游标格式由三段扩为
    四段「举报数:首报毫秒:目标 id:类型序」，首页哨兵类型序取 Integer.MAX_VALUE。新增目标类型
    时 case 表达式与 ReviewQueueService.typeRank 两处都要补档。
  E AppealService.submit 首行加 userService.requireUsableById(appellantId)，与举报同口径。
  F 申诉落库改 saveAndFlush 并捕获 DataIntegrityViolationException → 抛
    BizException(APPEAL_ALREADY_SUBMITTED)（409-006），把并发唯一键冲突映射为 409 而非 500。

过程中撞到的一个坎

R-22 安全响应头加固（CSP / X-Frame-Options / nosniff / Referrer / Permissions）
--------------------------------------------------------------------------------
[2026-10-06]  类型：安全加固  状态：已交付（后端 API + 前端 SPA 构建产物）
来源：R-22 之前的安全质询——「接口是否都带 token、URL 是否暴露 token、逆向能否击穿后端」
      逐项查证后如实列出 6 项残余风险，其中「无 CSP / 无安全响应头」经用户批准先行加固。

现象
  前后端均未下发任何安全响应头：无 Content-Security-Policy，无 X-Frame-Options，
  无 X-Content-Type-Options，无 Referrer-Policy，无 Permissions-Policy。一旦出现 XSS
  注入点，浏览器没有任何第二道防线；页面也可被任意站点以 iframe 嵌套（点击劫持）。

根因
  Spring Security 默认头策略未显式配置；前端为纯静态产物，托管服务器也不发头。

处理（两层，因为后端 API 与前端 SPA 是两套策略）
  A 后端 API 响应（只返回 JSON 与图片，不托管 SPA 页面）
    SecurityConfig.headers：
      Content-Security-Policy: default-src 'none'; base-uri 'none';
                               frame-ancestors 'none'; form-action 'none'
      X-Frame-Options: DENY（CSP 的 frame-ancestors 在旧浏览器不生效，做双保险）
      X-Content-Type-Options: nosniff
      Referrer-Policy: no-referrer
      Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()
    取最严格 'none' 的前提：已查证 src/main/resources/static/ 无 index.html，
    后端不托管任何页面（仅有 StorageWebConfig 的 /uploads/** 资源映射）。若将来改由
    后端直接托管 SPA，必须放宽此策略，否则页面自身的脚本与样式会被自身头拦死。

  B 前端 SPA 页面（由独立静态服务器托管）
    在 vite.config.ts 增加插件 contentSecurityPolicy()，transformIndexHtml + apply: 'build'，
    生产构建时往 index.html 的 head 顶部注入 meta：
      default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
      img-src 'self' data: blob:; font-src 'self'; connect-src 'self';
      base-uri 'none'; object-src 'none'; form-action 'self'
    只在构建期注入：开发期 Vite 以 JS 动态插入 <style> 并建立 HMR WebSocket，与严格策略冲突。
    style-src 保留 'unsafe-inline' 兼容运行时注入的少量 <style>；connect-src 'self' 依据
    「接口默认同源（/api 由反向代理转发）」，若部署为跨域 API 必须补上其 origin。
    img-src 的 data: blob: 当前未被用到（图片恒为 /uploads 同源地址），**经用户裁决保留**，
    留给客户端本地预览（将来用 FileReader / URL.createObjectURL 做上传前预览时必需）——

R-15 软删评论残留不可达的 like_record（孤儿点赞行）
--------------------------------------------------------------------------------
[2026-10-06]  类型：后端缺陷（数据卫生）  状态：已解决（方案 1 的收紧版：只在不可撤回的删除路径上清理）

  现象
    清理本地测试数据时点表发现 like_record 有一行 target_type=COMMENT, target_id=1,
    user_id=7，而该评论 status 已是 REMOVED（软删）。

  根因
    评论删除是软删（CommentService.delete 把 status 置为 REMOVED），但同事务没有清理该目标
    上的 like_record。点赞记录用 (target_type, target_id) 定位，目标软删后这些行既不会被读取
    也不会被回收。

  影响
    低危——点赞数按 target 现查，不会把已删评论的赞算进任何展示；但垃圾行会随删除量无限累积。
    同样的隐患将来会出现在帖子下架/删除上（P2 起涉及）。

  候选方案（需人决策，不擅自选）
    1) 删除/下架时在同一事务内硬删该目标的 like_record——最干净，但下架若可撤销
       （TakenDown → Approved）就得重建点赞，会丢数据
    2) 保留点赞行，只在下架态不参与计数；另加低频清理任务回收长期不可达的行
    3) 维持现状，接受垃圾行累积（需先确认量级上限）

  倾向
    方案 2 与不变量 #5 的「下架可申诉恢复」相容；方案 1 对评论删除安全、对帖子下架不安全。

  处理
    （2026-10-06，用户授权「你选就行了」）采纳方案 1 的收紧版——只在不可撤回的删除路径上清理。
    评论删除是软删且没有恢复入口，因此 CommentService.delete 在同一事务内调用新增的
    LikeRepository.deleteByTargets(COMMENT, removedIds)，把一级评论与连带移除的回复的点赞行
    一并硬删；帖子侧不动，因为下架可申诉恢复（TakenDown → Approved），硬删会丢点赞，留到 P2
    设计下架流程时再定。不选方案 2 的理由：低频清理任务是为一个已被根治的场景引入常驻组件，

    清理；集成测 PostFlowIntegrationTest.shouldPurgeCommentLikesOnDelete 用真实 MySQL 断言

  现象

  根因

    setTimeout(() => dismissToast(toast.id), TOAST_DURATION_MS)，时长定为 4000ms；手动关闭
    时 dismissToast 因找不到 id 而安全跳过。

  验证
    useToast.spec.ts 3 例全绿（含 vi.useFakeTimers() 验证 4 秒自动消失、手动关闭不误删后续
    提示）。

================================================================================
三、经验（跨条目，务必延续）
================================================================================

1. 几何正确 ≠ 视觉正确。验证叠压、遮挡、裁切类问题，不能只读 getBoundingClientRect——
   它返回的是元素矩形，不含绘制顺序与裁剪信息。R-09 因此被连续两轮检查漏过。正确做法：
   elementFromPoint 探测关键点、或做像素采样。

2. jsdom 没有布局引擎，图层、遮挡、溢出这类问题无法用单测覆盖，断言 class 名只是同义反复。
   这类 bug 只能靠浏览器实测兜底，等 P1 接入 Playwright 后应补端到端断言。

3. 改名/重构时，手写 CSS 是盲区。变量改名不会有编译错误，只有浏览器里才看得见。这类重构
   必须配一次浏览器实测（R-03）。

4. 修 bug 先写能复现的失败测试。R-04 是这条的正面样本：先让 useToast.spec.ts 出 2 个失败，
   再改实现，最后全绿。

5. 语义色的对比度要按用途分档。同一个主色，"大面积装饰"和"承载小字号文字"的要求完全不同；
   #2E8B7A 只能用于前者。危险色同理：danger 管「白字填充底」，danger-deep 管「浅色底上的
   文字」。规则已写进 uno.config.ts 注释（R-08、R-11）。

6. 错误提示只能有一个出口。请求错误一律由 http.ts 拦截器弹窗，页面不得内联渲染，否则必然
   重复（R-06）。

7. 不要为展示差异在请求层开洞。R-06 第一版用 errorToast: false 让调用方决定是否弹窗，被
   否决——展示策略应统一在拦截器，调用方只关心成功与失败。

8. 对比度有两类阈值，改一类会牵动另一类。文字对比是 4.5:1、非文本组件（图标、边框、色块
   边界）是 3:1。R-11 为了让未激活徽标的数字达标而调浅其底色，数字从 4.41 升到 4.70，但徽标
   圆本身对白底的对比反而从 1.15 掉到 1.08。量对比度必须同时算「文字/其底色」与「组件/其
   背景」两组，不能只算被点名的那一处。

9. 把 repository.save 全部 mock 掉的单测，测不到任何数据库约束。R-13 的 NOT NULL 冲突在 15 例
   PostServiceTest 里毫无征兆，只有真实 MySQL 的集成测试一跑就炸。凡是「列约束 / 唯一键 /
   外键 / 默认值」相关的行为，必须由 @DataJpaTest 或端到端集成测试兜底，Mockito 单测不能
   算数。

10. 跨前后端的资源路径要单独确认代理。R-14 的 /uploads 不属于 /api，代理规则只覆盖 /api 时
    前端一切正常、只有图片静默 404。新增任何非 /api 前缀的对外路径（静态资源、回调、
    WebSocket），都要同步检查。

11. 门禁要写成「漏写即失败」，不能「漏写即放行」，并且必须反向验证一次。R-16 能溜过去，是
    因为白名单只活在文档里。ModuleBoundaryTest 采用「动态发现模块 + 未登记即只允许依赖
    common」，于是新增模块忘了登记就是构建失败而非静默通过。写完门禁还要故意制造一次违规看
    它是否真红（本项目做法：临时去掉 comment 的 post，确认报 8 处违规）——永远为真的断言等于
    没写。

12. 非文本对比度不达标时，先问「这个元素非画不可吗」。R-18 的未激活圆对白底只有 1.08:1，
    加描边会让未激活态比激活态还重；直接不画，问题连同视觉负担一起消失。但只要它承载信息
    （如进度），就不能按装饰处理，必须正面达标。

13. 无状态令牌（JWT）下，「登录时校验过了」不构成任何保证。R-19 B 项的现场：封禁发生后，
    旧令牌在有效期内（2h）畅通无阻地继续发帖 / 评论 / 点赞 / 上传。凡是账号级禁令（封禁、
    黑名单、降权），都必须在每个写入口重新判定；只读入口可放行以保留浏览能力。同时规则要
    收敛到单一出处（本项目为 UserService.assertUsable），否则「一处收紧、另一处漏」几乎是
    必然。

14. 实体上的计数器不能用读-改-写。R-19 C 项：无 @Version 的 count++ 在并发下必丢更新，单测
    （mock 掉 repository）完全测不出来。正确做法是原子 UPDATE ... SET c = c ± ?。用
    @Modifying 时还要想清持久化上下文：批量更新绕过一级缓存，同一事务内随后再读该行会拿到
    旧值（需要 clearAutomatically），而清除前必须先 flushAutomatically 落定本事务尚未刷出的
    改动（否则 comment.remove() 这类脏数据会被连带丢弃）。

15. 校验「目标存在」不等于校验「目标可访问」。R-19 A 项：评论点赞只查了评论在不在，没查它
    所属帖子是否可见，于是下架帖成了可读写后门。凡是挂在父资源下的子资源（评论之于帖子、
    文件之于帖子），写入口都必须连同父资源的可见性 / 状态一起校验。

16. 一次性凭证要「抢占式消费」，且消费记录的存活期必须覆盖凭证本身的有效期。R-20 J 项：
    emailToken 带 jti，绑定前先 markUsedOnce 占位，占不到即视为重放——抢占式（而非成功后
    再记）才能让并发请求里只有一个进入创建流程；消费记录的 TTL 取 emailTokenTtl，短于此则
    记录先失效、凭证又能被重放。凭证签名只证明「这是本服务签发的」，不证明「没被用过」。

17. 含密钥的本地配置绝不能放在 src/main/resources。R-20 N 项：resources 下的文件会被打进
    target/classes 与产物 jar，application-local.yml（AES key / email pepper / JWT secret）
    因此进了构建产物。改放 qinglan-server/config/ 后由 Spring Boot 默认的 file:./config/
    加载，启动命令不变；换位置后要手工删掉 target 下的陈旧副本，否则它仍在 classpath 上。

18. 限流要放在校验之前，否则绕过成本为零。R-20 H 项：若先校验格式再计数，攻击者拿一批坏
    文件即可无限次请求而不消耗配额。顺序应为「可写状态 → 频次 → 格式」，让非法请求同样
    计入窗口。

19. 一列承载多种语义，前端必然猜错。R-21 A 项：post.review_reason 在下架时存「类型码[: 说明]」、
    驳回时存自由文本，再叠加「恢复后仍残留旧值」，前端用「是否非空」根本分不清三态。判据要
    用显式的状态字段（本项目新增 takenDown 布尔），不能让前端从字符串内容反推状态；同时
    「处罚被撤销」时应在实体上清空当前理由（历史留在只增不改的审计表），否则恢复后的内容会
    一直挂着失效的处罚说明。表现形式不同、语义不同的数据，宁可分开字段，也不要塞进同一列。

20. 全局浮层的 z-index 不能与既有元素撞值。R-21 B 项：举报弹层初版用 z-50，与 sticky 页头
    同值，谁在上面只取决于 DOM 顺序，一次组件搬动就会翻转。应为页面确定一份固定的分层刻度
    （本项目：页头 z-50 < 弹层 z-[900] < 全局提示 z-[1000]）并写进组件注释，而不是各自随手
    挑一个「够大」的数。

21. 集成测试里用 JdbcTemplate 直查，必须先 flush 持久化上下文。R-21 C 项：JPA 把 flush 推迟
    到事务提交，JdbcTemplate 又完全绕过一级缓存，于是读库拿到的是事务开始时的旧值，出现
    「实体已迁移、库里还是旧状态」的假失败。凡在测试内混合「JPA 写 + JdbcTemplate 读」，读之
    前都要显式 entityManager.flush()。这与第 14 条同源——持久化上下文与数据库之间有两层缓存，
    混用工具时最容易踩。

22. CSP 没有「一份通用模板」，要按「这个响应返回什么」分档。R-22：后端只返回 JSON 与图片、
    不托管任何页面，可取最严的 default-src 'none'（被注入的内容连子资源都加载不了）；前端 SPA
    必须放行自身的脚本与样式，只能取 'self'。给 API 套 SPA 策略等于白写，给 SPA 套 'none' 则
    页面直接白屏。写策略前先查清「这个端点到底吐什么」，并把这个前提写进注释——本项目后端
    CSP 的 'none' 就绑定在「后端不托管 SPA」上，将来若改由后端托管页面，必须同步放宽。

23. 安全头能拦住的攻击面与它自身的盲区都要写清楚，别造成「加了头就安全」的错觉。R-22：
    （a）frame-ancestors 写在 <meta> 里会被浏览器直接忽略，防 iframe 嵌套必须由托管页面
    的服务器发响应头，前端构建插件覆盖不到——只在构建产物里加 meta 不等于防住了点击劫持；
    （b）安全头只是纵深防御的第二道墙，第一位的仍是「不产生 XSS 注入点」（本项目全程无
    v-html、无 innerHTML 拼用户输入），头不能替代输出编码。
    另外：头部类改动必须浏览器实测。响应头存在与否、CSP 有无违规（Refused to load/execute/
    apply style）只有真实浏览器能暴露，MockMvc 只能断言「头被写出来了」，断言不了「页面
    在策略下仍能正常工作」。

24. -Werror 门禁的真实价值在「拦住后来废弃的 API」，而不只是拦住新写的坏代码。R-22 C 项：
    SecurityConfig 用了 Spring Security 6.5 已标记 @Deprecated 的 permissionsPolicy(Customizer)，
    编译期直接红。判断「哪个是替代 API」不能靠猜，用 javap -v 比对两个候选成员的 Deprecated
    标记最可靠（本项目据此确认应改用 permissionsPolicyHeader(Customizer)）。这是 R-17 立的
    编译门禁第二次拦下废弃调用，与第 11 条同理——门禁要常驻，且要真的能红。

25. 「已经是目标态」不等于「非法迁移」，幂等入口要先短路。R-23 A 项：restore 只考虑了
    TakenDown → Approved，当帖子已被他人手工恢复成 Approved 时，复审再走一次 Approved →
    Approved 会被状态机判非法并整体回滚，连带把申诉状态也退回。凡是从外部可重复触发的状态
    迁移（复审、重试、回调），入口都要先判「是否已经是目标态」，是则直接返回，而不是硬闯
    状态机。判据要用显式的状态字段，不要从别的字段反推（与第 19 条同源）。

26. 「系统先动手、人后确认」的流程，必须把人工终态动作单独做出来。R-23 B 项：举报数达阈值
    自动下架时举报刻意保持 PENDING 好留在队列，但只做了自动下架、没做「人工确认举报成立」，
    于是管理员要么走首次下架（对已下架内容非法），要么走驳回举报（语义是「内容不违规」），
    举报永远清不掉。补动作时语义不能与相邻动作混淆（「维持下架」≠「驳回举报」）——相邻动作
    名字相近但语义相反时，最容易漏掉其中一个。

27. 排序键与游标必须覆盖「全部可能撞号的列」。R-23 D 项：target_id 只在各自类型内唯一，帖子
    #7 与评论 #7 会撞号；只按 reportCount/firstReportedAt/targetId 三键分页，两键并列时无法
    区分，翻页会漏行或重复。复合游标要包含能把每行唯一确定的全部列，且 having 的比较顺序
    必须与 order by 严格一致。另：JPQL 里 case ... then 0 else 1 end 的 0/1 字面量被 Hibernate
    推断为 Integer，对应参数必须声明 int——声明成 long 时首页哨兵 Long.MAX_VALUE 会在绑定
    参数处直接抛 InvalidDataAccessApiUsage（表现为接口 500），而单测用 mock 完全看不出来。

28. 同一个「写入口家族」（举报 / 申诉 / 评论…）的校验步骤要对齐。R-23 E/F 项：申诉比举报少了
    requireUsableById（封禁账号仍可申诉）与唯一键冲突的 409 映射（并发重复提交抛 500）。多个
    写入口做同类事情时，把公共校验抽到一处、或至少维护一份 checklist，否则「一处收紧、另一处
    漏」几乎必然发生（与第 13 条同源）。约定好的错误码（如重复提交 409）必须显式捕获约束
    异常去映射，不能指望全局兜底自动给出正确的状态码。

29. 验证脚本自己的错报，比产品缺陷更容易骗过自己。R-24 的接口级端到端脚本在调用
    POST /api/admin/posts/{id}/approve 时返回了空状态（无 statusCode、无响应体），我据此写下
    「审核未生效」；实际该接口 18ms 就返回 200、库里状态已变、通知也已发出——问题出在脚本
    用的 mysql 客户端把密码警告写到 stderr，而 PowerShell 5.1 在 ErrorActionPreference=Stop 下
    会把原生命令的 stderr 当成致命错误。教训有两条：探针报出「奇怪的状态码」时，先用另一条
    通道（直连接口、查库）交叉确认，再下结论；原生命令不要用 -p<密码>，改用环境变量传凭据。

30. 「改的是全局组件」这件事必须显式检查。R-24 把 AppHeader 的容器宽度写死成 1200px，而它作用
    于全部学生端页面，于是 4 个内容仍为 720px 的页面头部与内容左边缘错开 232px。当时的实现计划
    里还写着「其余 4 个页面零改动」——文件确实没改，但视觉效果被改了。改 props、容器类、全局
    样式这类横向影响面时，先列出受影响页面清单，并让「头部的容器宽度」与「内容的容器宽度」
    由同一个判断驱动，而不是各自决定。

31. 不要在同一轮里让两个子代理改同一个文件。R-24 的 T5 与 T6 都被要求往 App.vue 接线，结果
    并发提交把对方的 import 顶掉过，虽然最终补齐且测试全绿，但合并后的文件没经过逐行审查、
    提交归属也乱了。并行拆分必须以「文件零重叠」为准，公共入口文件只交给一个执行者。

32. EXPLAIN 的结论依赖数据量。R-24 对三张刚刚建好的空表跑 EXPLAIN，优化器给出的 rows 全是 1、
    选中的索引带有随机性（通知列表本可走 (user_id, id) 免排序，实际却选了另一个索引并产生
    filesort）。空表上的 EXPLAIN 只能证明「索引存在且可被选中」，不能证明「生产规模下是最优
    计划」。这条结论要么在造数后重跑，要么在文档里标明局限，不要当成功效验证。

33. 全局提示的层级必须高于第三方组件库的弹层。Element Plus 的 defaultInitialZIndex 是 2000 且
    每开一个弹层递增，而我们自己的层级注释只写到 1000——于是「管理端弹窗内请求失败」的提示被
    遮罩压在下面：看不见也点不掉，而按第七章的错误唯一出口约定页面又不会内联渲染它。引入第三方
    弹层时，先查它的默认层级常量，再把全站 z 轴口径写成一处唯一来源（本项目在 uno.config.ts 的
    theme.zIndex），不要散落在各组件里靠注释约定。

34. 自定义 UnoCSS 主题键必须核对构建产物。theme.zIndex 加了键之后，z-toast 这类类名到底有没有
    被生成，dev 与单测都看不出来——不生成就是静默失效，比写错颜色更难发现。改完先 build + 在
    dist 的 CSS 里 grep 一次，再往下做。同理适用于任何新增的 theme 键（spacing、breakpoint 等）。

35. 事件的 .stop 与 .prevent 不能互相替代。stopPropagation 只拦监听器，不阻止浏览器的默认行为；
    锚点 (<a>) 内的按钮两种都要：.stop 让 Vue Router 的 guardEvent 拿不到事件（不 push），
    .prevent 取消 <a> 的默认跳转，否则用户仍会被带去做整页导航。

36. 修好行为不等于消除结构缺陷。`<button>` 嵌在 `<a>` 里用 `.prevent.stop` 能修正行为，但结构
    依然非法、语义依然混乱；重构结构往往有代价（本次是可点区域缩小）。这类取舍要显式权衡，
    并把「只修了行为」记进待办，不要让后来者以为它已经干净了。

37. 测试断言实现细节会反过来锁死规范。BaseCard.spec 断言 `sm:p-6`，于是把 `sm:` 改写成
    `max-sm:`（AGENTS.md 第七章）必须先改测试——这正是 T-19 拖了一轮的真实原因（当时的备注写的是
    「怕影响既有断言」，没写清是这条）。断言应落在结构或行为上（如「基线 + 收窄」这层关系），
    而不是某个具体的原子类名或列下标。

38. jsdom 不实现 label 的激活行为。R-25 里「点分组标题把单选值改掉」这类由 HTML 规范决定的缺陷，
    没法用 click 在单测里复现（点了不会激活控件）。可行的办法是断言**结构**（radio 的祖先里不能
    再有第二个 label），并在注释里写清为什么用结构断言、以及为什么不能用行为断言。

39. 同一份「登录态」不能有两个来源。R-26 的根因是 store 的内存态与请求头的持久化态各写一半：
    存储不可用时二者分歧，表现为「已登录却全 401」。修法是把唯一权威放内存、持久化只做跨刷新
    兜底，并把读写收进 api/http 的一对函数——凡是需要跨模块共享的状态，都要先回答「谁是权威」。
    副作用：模块级状态不会在测试间自动复位，凡依赖它的 spec 必须在 beforeEach 里显式清零
    （R-26 里 useNotifications.spec 因此补了 setAuthToken(null)），否则「已登录」用例会漏进
    「未登录」用例。

40. 断言要断到「语义那一层」。整段文本 toContain('2')、toBeTruthy 这类零头断言，在日期时间或
    任意非空值面前都会「恰好通过」，等于没测。R-26 把它们改成「举报数单元格文本恰为 2」「deviceId
    匹配 UUID」。判断标准：撤掉被测逻辑后断言是否还会通过——会通过就说明断错了层。

41. 拦截型流程（先审后发、强制阅读这类）必须连「谁放行」一起交付。R-30：状态机、落 PENDING、
    428 兜底都做了，唯独没做放行入口——结果是一条没有任何人能通过的路径；更糟的是写入口（发帖）
    本身正常返回 200，所以单测、联调、CR 都不会报错，只有真的走一遍全流程才看得见。凡新增一个
    「需要人介入才能继续」的状态，就要同时回答三问：谁看得见它（列表/队列）、谁裁决它（动作入口）、
    裁决之后它去哪（可见性 / 通知）。判据可以很土但很硬：让一个新用户按正常操作自己走到终点。
    延伸：既有的同类面板（这里是举报队列）不能被当成「审核入口已具备」——两个来源不同的流程
    （举报驱动 vs 先审后发）各有各的入口，不能互相顶替。

42. 「有没有索引」要问「查询形态与现有索引前缀是否匹配」，不能靠感觉或表格行数。R-31 的六处缺口
    全部是先读出 Repository 的 where/order by，再与索引前缀逐一对照找出来的；真正的证据来自造数
    后的 EXPLAIN：同一张表在造数前 type=index（看起来「用上索引了」），造数后才露出它扫了 49880 行
    属于全索引扫描，而另一处干脆是 type=ALL + Using filesort。空表上的 EXPLAIN 在这个问题上会给出
    误导性的乐观结论（与经验 #32 同源，但方向相反：32 说的是别把空表结论当成功效，这里说的是空表
    根本暴露不了缺口）。补充两条：一、结论必须写清「在什么数据量下、哪些查询、加索引前后分别是什么
    plan」，否则后来者无法复核；二、加了索引不等于优化器一定选它——status IN (两个值) 这种形态可能
    仍走旧索引 + filesort，要把这个保留一并写进迁移文件头。

43. 审计结论必须回源码复核，且要区分「缺陷」与「当事人在当时有意留下的取舍」。R-31 里子代理报了
    十余条，逐条读代码后收敛为 9 条；其中「BLACKLISTED 无入口」「处置不扣分」「通知不聚合」等其实
    早已躺在待办里，属产品未定的取舍，不是新发现的漏洞——把它们混进修复清单会平白改动产品行为。
    做法：报告里把「已确认缺陷」与「已核实但需决策」分成两节，后者的每条都写清「为什么不擅自改」。

44. 本地绿 ≠ 仓库能跑。R-32：`application.yml` 含本地密钥、必须 gitignore，但一旦测试配置依赖它，
    干净的 checkout（CI 就是）就成了另一套环境——`@SpringBootTest` 直接起不来，而本地永远绿。
    判据：把「只有本机才有的东西」从 classpath 上移走再跑一遍。本项目的手法最省事：**不 clean**、
    删掉 `target/classes/<本地配置>`（其余资源仍在），跑测试时加 `-Dmaven.resources.skip=true`
    阻止它被重新拷贝——比另 clone 一份仓库快得多，而且与 CI 的 classpath 等价。
    对应的书写要求：测试 profile 必须自成一套，并在文件头写明「删了就会红」，否则下一个人会把某段
    配置删回去（本次就补了 qinglan.post / upload / announcement / moderation / storage 五段）。

45. 审计报出的「待确认」不能留着不管。R-31 留了 6 条「待确认」，R-32 逐条实证后的分布是：
    1 条真缺陷（复审独立性可绕过）、1 条不是缺陷（上传并发实际不可达）、其余是产品/架构决策。
    三种结论都要落文档：真缺陷进修复清单；**不是缺陷的也要写进「已核实但不是缺陷」并给出否证依据**
    （否则下一轮审计还会把它当疑点重新翻一遍，白烧时间）；决策项进待办并写明为何不擅自改。

46. 改一个「已被别人调用的公开端点」，改动面是「端点 + 全部调用方 + 调用方的测试 + 前端」，不是
    端点本身。R-34 把 take-down 等四个处置端点从「直接处置」改成「发起提案」：请求体去掉 banDays、
    入参从自由文本改成 {reasonCode, detail}、出参从 Void 变成 {proposalId}。少改一处的表现往往
    不是编译错误——后端测试照样能跑，只是断言测的已经是另一件事了。做法：动手前先 grep 出全部
    调用点（含 spec 与前端 api 层）列成清单，逐个改完再跑门禁。同时要分清两类改动：「语义等价的
    替换」可以静默做，「能力被移除」必须显式告知使用方（banDays 属于后者，本轮先问用户再动）。

47. 设计文档里互相冲突的两处，要以「决策」为准并向用户复核，不能挑一处默默实现。R-34 撞上过一次：
    方案 7.1 的端点映射表把 restore / show-contact 也标成「二期改为发起提案」，而决策 D5 与动作
    枚举里根本没有这两个动作（它们是放行/纠错，不表决）。这种冲突不是笔误，是实现前必须消解的
    分叉——本轮把三处分歧（端点改造方式、banDays 归属、restore 是否表决）一次性列成选项交用户定，
    再把结论回写方案十五节。判据：凡是「选了 A 就要重做一遍」的地方，都值得先问一句。

48. 「文档与实现不一致」要先分类再动手，不能一律照文档、也不能一律照现状。R-34 复核出三类：
    ① **文档笔误**（open_target_key 写 CHAR(40)，但实体映射是 varchar，validate 会直接拒）→ 按实现；
    ② **文档更对**（resolved_by 文档写「裁决人」，实现误写成发起人）→ 按文档改，而且这条不只是
       措辞问题：它让「是否超管拍板」不可判定，进而使「不采用 DECIDED_BY_SUPER 状态」这个决定
       本身失去依据——**一个语义错误可以悄悄废掉另一处设计决策**，这正是要逐条复核而不是抽样看的
       原因；③ **实现有缺口**（设计 9.2 要求队列行内显示提案进度，初版没做）→ 补做。
    分类之后的动作很不一样：①只需改注释，②要改代码 + 补断言，③要跨前后端加功能。先分类再排期，
    能避免把「改注释」的工作量估成「改功能」。

49. 「文档漏写」不等于「可以随便定」，也不等于「可以不做」。R-34 里有两处文档完全没提：分母下界
    钳制（票数可能超过快照）与快照下界取 1（委员会为空时超管发起）。两者都不是审美选择——不处理
    就是 IllegalArgumentException → 500。遇到这种空洞，先问「不做会怎样」，再问「有没有更严的
    做法」：更严的做法（拒绝新成员投票）需要系统记录「某人何时进入委员会」，而表里根本没有这个
    时间，所以只能取方向安全的钳制，并把「为什么不能更严」一并写进注释与文档。

50. 「作出处置」与「撤销处置」的权限要分开定级，不能默认对称。R-34 追加修正：下架/隐藏联系方式
    都需**委员会表决**才成立，而撤销它们当初是**单人**动作——两侧不对称，等于少数可静默推翻多数决，
    表决形同虚设。修法不是把撤销也塞进表决（会让申诉通过卡在投票上），而是**提升撤销的档位**：
    新增 DISPOSITION_REVOKE（仅超管），与 PROPOSAL_ARBITRATE 同档。
    判断分界线的一个好用的问法：**「有没有人申请」**——无人申请的静默撤销需要最高级别；
    被处置人主动提出、有独立复审人、全程留痕的程序性撤销（申诉）可以留在原级别。
    这条也顺带解释了一个常见困惑：为什么「撤销」往往比「作出」更需要高权限——
    作出有流程约束（表决、举报、审核），静默撤销没有任何约束。

51. 权限点收紧后，**门禁会抓住你没预料到的连带影响**，别把它当成麻烦。R-34 收紧 restore 的权限点后，
    ReviewFlowIntegrationTest 里一条与权限无关的用例（复审撞上「已恢复」的幂等场景）红了——
    它的造数用 ADMIN 令牌打 HTTP 做「手工恢复」。这不是测试脆弱，恰恰是它在提醒：该动作的真实
    执行者变了（现在是超管）。做法是改造成真实流程（换 SUPER_ADMIN 令牌）而不是绕过端点直接调
    service；同理，权限矩阵测试里的「超管专属点」清单也强制新点被显式登记。
    结论：新增/收紧一个权限点时，预期至少红两处（矩阵测试 + 某个造数用例），把它们当作清单用。

52. 判断「死代码」看的是**有没有入口**，不是「有没有测试通过」。R-35 审计里抓到的 banDays 分支：
    二期把 take-down 端点改成发起提案后，服务层那条封禁分支再也没有任何调用方能传非 null 进来，
    但它的单测一直绿着（单测直接调服务方法，绕过了 HTTP 入口）——于是「测试通过」反过来掩盖了
    「功能已不可达」。判据很具体：**从最外层入口（Controller / 定时任务 / 消息消费）开始反查调用链**，
    走不到的 public 方法就是死的，测试再多也不算数。
    由此得出一条改造清单：改掉一个入口的调用方式后，要专门回头看一眼「原来由它触发的下游分支
    还有没有人能触发」，并顺手把随之失效的测试一起删——留着它比删掉更危险，它会让下一个人以为
    那个功能还在。

53. 可访问性问题的特点是「框架不默认给、肉眼测不出、但真实用户会被挡住」。R-40 的 62 项里没有
    一项会让普通鼠标用户察觉，但「公告正文滚动区无 tabindex」会让键盘用户永远滚不到底、强制阅读
    弹窗关不掉——a11y 缺陷可以直接等于功能不可用，不只是体验优化。这类属性靠 code review 肉眼
    看不住，要靠一份外部清单（本轮是 Vercel Web Interface Guidelines）定期过；修法优先级是
    「全局一处兜底」优先（reduced-motion 媒体查询放 main.css 一处、焦点环用 peer-focus-visible
    类），而不是每个组件各写一遍；同时区分「纯属性修复」（可顺手做）与「行为变更」（筛选入 URL、
    disabled 改提交时校验），后者必须登记待办、不能混在 a11y 轮次里改了产品交互。

54. 规格审查要把「全部定稿文档 + 修复台账」当双基线，并三分类「缺失 / 偏离 / 有意演进」。R-41
    发现设计文档自身有跨章张力（26 行五要素硬拦截 vs 4.3 放宽脱敏；流程图默认通过 vs 硬红线
    先审后发）、跨文档演进（收藏从 MVP 降到生产化 P2；即时下架被 P5 提案化；dismiss 单条改
    聚合批量）。只拿最早的设计方案逐条对账，会把有意演进误报成缺陷；不读台账又会重复登记
    T-13 / T-15 这类已知缺口。有效做法：有证据的缺失才开待办；后续方案明确改写过的，在审查
    记录里沿演进链留痕说明；文档自相矛盾的（如正文手机号口径），登记为「需产品拍板」并写清
    各选项，而不是替产品选一个实现。大范围对账可让并行子代理分路取证，但涉及行为闭环 / 权限
    语义的高价值结论（R-41 的 T-43）主笔必须回源码复核二手结论——子代理能找到线索，闭环判断
    与权限连带影响要自己走完。

55. 抽公共组件的正序是「全量只读盘点 → 每个候选附 ≥2 处真实消费点证据 → 方案分批获批 →
    新建件带 spec 并一次性迁完消费点」，不能凭印象抽、更不能边写边发现新重复。R-42 先审计
    三包 53 个组件才动手：爱心 SVG 三处逐字相同、加载更多 12 处、三态 14+ 处、倒计时两份
    逐字复制——这些重复靠「读一个文件时的感觉」永远数不全。两个具体教训：①「组件太小不
    值得改」往往就是根因——公告框问题不是宽度数值，是 Reader 把卡片外壳与正文呈现耦合，
    直接调宽度只会制造卡里卡；公共组件要剥到「尺寸 100% 由外壳决定」才算边界干净。
    ②机械迁移会改变隐性契约：title 从 td 移到内部 time 后，按 td[title] 定位的 5 条旧测试
    全红——抽组件时必须同步搜索「被迁移 DOM 属性的所有断言」；断言改成新结构时定位意图
    不能变（R-42 改为 time[datetime] 定位，而非简单删断言）。

56. vitest 绿不等于类型对：esbuild 转译会擦除仅用于类型注解的 import/名称，测试运行时不报错，
    只有 vue-tsc（typecheck/build）能抓到 TS2304 一类问题。R-42 收尾时 QueueTable.spec
    漏删的 DOMWrapper 类型 import 正是测试全绿、build 爆红。改完测试后四道门禁（lint /
    typecheck / vitest / build）仍要全跑，「测试过了」不能替代类型检查。

57. 抽「布局 / 外壳」组件时，先定「谁持有语义容器」，并查宿主对 DOM 数量 / 语义的断言。R-48 抽
    TwoColumnLayout 时撞上过：ProfileView.spec 与 PublishView.spec 都断言 findAll('aside') 恰好
    1 个，而学生端侧栏组件（HomeSidebar）本身根节点就是 <aside>——若把它塞进布局的侧栏插槽，
    就会形成嵌套 aside，断言直接红。定法是：语义容器（<aside>/<main>）由布局组件独占，被嵌
    组件改为多根片段。做法上，抽件前把「宿主会断言的 DOM 数量与语义」grep 一遍
    （本项目即 findAll('aside') / findAll('section')），比事后改断言安全得多——这类断言恰恰是
    防止结构漂移的保护，不该为了迁就重构而放宽。
