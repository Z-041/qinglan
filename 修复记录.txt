R-28 前后台会话模型澄清与会话语义修复（单会话约定 + 退出跳转 + 角色口径统一）
--------------------------------------------------------------------------------
[2026-10-07]  类型：缺陷修复 + 约定澄清  状态：已交付
来源：用户指出「前端没区分学生端与管理端：后台登录与前台上登录是一样的，前台退出后后台也同时
      退出」。经核查属实，但**根因不是漏写隔离**，而是从设计上就是「一份令牌 + 一个 store」。
      先把事实与取舍摆清，由用户在两个产品决策上拍板（AGENTS.md 第十一章第 4 条），再动手。

核查结论（前端「前后台不分」的原因）

  1 令牌只有一份：api/http.ts 的 TOKEN_STORAGE_KEY = 'qinglan.access-token' 与模块级
    memoryToken，所有请求共用
  2 用户态只有一份：stores/user.ts 的 accessToken / profile
  3 两个登录页写的是同一个 store：useAuth 的 verify / bind 都调 userStore.setAccessToken()，
    不看区域
  4 两处退出也调同一个 signOut()：App.vue（学生端）与 AdminLayout.vue（管理端）
  5 后端同样只有一份身份：JWT 里就是 userId + role，没有「前台会话/后台会话」的概念

  故「前台登录＝后台登录」「前台退出＝后台退出」是该结构的必然结果，不是实现缺陷。

用户决策（本轮据此实施）
  - 会话模型：**保持单会话**，不拆双令牌；补严语义
  - 前台登录页遇到管理员账号：**允许登录，但明确提示当前身份**

修复

  1 前台退出不跳转（真缺陷，本轮核心）。App.vue 的 sign-out 只调 userStore.signOut()、
    不做导航，而路由守卫只在**导航时**运行——若当时在 /profile（requiresAuth），档案已清空、
    ProfileView 三个分支全不命中，页面只剩一个「我的」标题；在 /publish 则停在一张提交不了的
    表单上。管理端退出是有 router.replace('admin-login') 的，两边行为不一致。
    处理：App.vue 增 handleSignOut()——清登录态后，当前路由 meta.requiresAuth 为真则回首页；
    游客本就能浏览的页面（首页、详情）留在原地、自动切游客态，不打断浏览

  2 管理员从前台登录无任何身份提示。前台登录页不校验角色，管理员从前台登录后 /admin 守卫
    直接放行，导航栏那个角色徽标很容易被忽略、误以为在用学生身份。
    处理：LoginView 的 afterAuthenticated() 中，若当前角色属管理员则提示「当前为管理员账号，
    可访问管理后台」；**刻意不拒绝**（管理员同时是本站认证用户，挡在社区外与其身份冲突）

  3 角色准入口径此前有三份。router/index.ts 与 AdminLoginView.vue 各写一份 ADMIN_ROLES，
    本轮又要在 LoginView 判断一次，属第三处重复；三份一旦漂移就会出现「前端放行、后端 403」。
    处理：抽取到 types/user.ts 的 ADMIN_ROLES / isAdminRole()（唯一来源），三处改为引用

  4 约定写入 AGENTS.md 第七章：一个浏览器 = 一个账号 = 一份会话，并派生三条硬约束
    （退出必须跳转、管理员可从任一登录页进入但须提示身份、角色口径只有一份）；
    同时写明「若将来要同浏览器双身份登录，属架构变更（需双令牌 + 按区域切 Authorization），
    先提 issue」——把这次的取舍固化成规则，避免后来者就地乱改

验证
  - 前端 240 tests 全绿（45 文件；新增 App.spec.ts、LoginView.spec.ts）
  - pnpm vue-tsc --noEmit 无输出；pnpm lint（eslint .）无输出；pnpm build 通过
  - 反向验证：把 App.vue 的跳转去掉后，App.spec.ts 的用例确实变红
    （expected '/profile' to be '/'），证明它不是装饰性断言
  - 未做浏览器实测（本轮未启动服务）：前台退出跳转、管理员登录提示两项并入 T-24

R-26 前端静态复查 21 处（登录态同源 / 失败态 / 竞态 / 表单校验 / 可访问性 / 测试质量）
--------------------------------------------------------------------------------
[2026-10-07]  类型：缺陷修复  状态：已交付
来源：R-25 交付后对 qinglan-web 的第二轮静态复查，逐条读代码取证再动手，全程未启动服务。

修复（按处理顺序）

  1 存储不可用会把用户锁在「登录不进去」的死循环里。api/http 的存储读写已降级为「读 null /
    写忽略」，但 Pinia 里的 accessToken 只写内存、请求头却只读 localStorage——存储不可用时
    内存说已登录、请求却不带 Authorization，于是每个请求 401、被登出、重登还是同样结果。
    处理：http.ts 增内存态令牌 setAuthToken / getAuthToken（内存为准、存储负责跨刷新持久化），
    store 的 accessToken 与 setAccessToken 改用之，做到「内存态与请求头同源」

  2 用户管理改了筛选条件仍可点「加载更多」，把「新筛选 + 旧游标」拼在一起（重复行 / 漏行）。
    处理：useUserManage 记录「上一次成功查询的筛选快照」，筛选项与快照不一致时 loadMore 直接
    拒绝；视图在脏时禁用「加载更多」并提示先点「查询」

  3 管理端四张表把「加载失败」伪装成空态。用户表 / 审核队列 / 申诉队列 / 公告表的空行文案写死
    为「没有……」，一次网络故障即被说成「没有数据」。处理：useUserManage / useReviewQueue /
    useAppealQueue 与 AnnouncementManageView 各补 failed 状态位，四张表按 loading→failed→空态
    分三档渲染，失败档提示「加载失败，请点击『刷新』重试」

  4 审核上下文面板失败后留一片空白抽屉。处理：useReviewContext 补 failed，ReviewContextPanel
    增加失败分支给出说明（否则管理员只看到空抽屉、不知是没数据还是坏了）

  5 发帖页话题拉取失败：话题区永远空白、发布按钮永远灰着却不说为什么。处理：usePublish 补
    topicsFailed，PublishView 在话题区给出「重试」

  6 并发 401 会弹 N 条提示、跳 N 次登录页。首屏常并发多个请求，令牌失效时它们同时返回 401，
    拦截器逐个弹 toast 并调 unauthorizedHandler。处理：加「已处理」闸，重新登录取到令牌时解除
    抑制；并补「并发 401 只处理一次」用例

  7 requiresAdmin 守卫在拿不到档案（401 或网络故障）时回首页，既覆盖掉拦截器已发出的跳转，也让
    令牌失效的管理员以为「后台入口没了」。处理：改为回管理端登录页并带上 redirect

  8 选图超出上限被静默丢弃（选了 12 张只上 9 张，用户以为都传上了）。处理：useImageUpload 在
    已满与超限两种情形都 toast 告知（含忽略了几张），并补用例

  9 自证式测试。useImageUpload.spec 把调用方的合并逻辑抄进测试，只验证了测试自己、与
    PublishView.handleSelectImages 无关。处理：删除该用例，改为在 PublishView.spec 挂真实组件、
    走真实处理器，验证「上传在途时删除的图不会被复活」

 10 PublishView.spec 弱断言。用整段文本 toContain 断言发布须知，PC 右栏与窄屏表单内两处只要
    有一处存在就通过。处理：改为断言恰好两处 <p> 命中该文案

 11 队列与通知翻页缺请求序号、刷新失败不清列表与游标（useReviewQueue / useAppealQueue /
    useNotifications 同型于 useFeed）。处理：三者补 requestSeq（丢弃过期响应）与「刷新先清列表
    与游标」，loadMore 记下发起时序号

R-23 P2 审核体系复审（6 处缺陷：幂等 / 终态 / 可逆性 / 游标 / 写入口 / 并发）
--------------------------------------------------------------------------------
[2026-10-06]  类型：缺陷修复（P2 复审）  状态：已交付
来源：对 P2 审核体系做代码审查（两个子代理交叉验证），6 条全部成立、无一误报；
      经用户批准「全部修复」。

现象（6 条）
  1 ReviewService.restore 缺幂等：帖子已是 Approved（他人已手工恢复）时，复审通过走
    Approved → Approved，状态机判为非法迁移抛 ILLEGAL_REVIEW_TRANSITION，整个复审事务
    回滚，连申诉状态也一并退回。
  2 自动降级后举报无合法结案入口：举报数达阈值自动下架时，举报刻意保持 PENDING 以留在队列，
    但管理员认同下架时既不能走 takeDown（TakenDown → TakenDown 非法），走 dismissReports 又
    把它记成「内容不违规」（DISMISSED），与事实矛盾。举报永远挂在队列里。
  3 「隐藏联系方式」不可逆：Post.showContact() 是死代码，没有任何处置能恢复可见性，一次
    误判即永久生效。
  4 审核队列游标缺 target_type：target_id 只在各自类型内唯一（帖子 #7 与评论 #7 撞号），
    若两者举报数与首报时间并列，仅凭 target_id 无法区分，翻页会漏行或重复。
  5 AppealService.submit 未校验账号可用：与 ReportService.report 口径不一致，被封禁账号
    仍可提交申诉。
  6 并发重复申诉抛 DataIntegrityViolationException：uk_appeal_target 挡住后落到全局
    catch-all 500，而非约定的 409。

根因
  1 状态机 APPROVED 的合法后继只有 TAKEN_DOWN（不含自身），restore 未对「已经是目标态」做
    短路，把「无需迁移」当成了「非法迁移」。
  2 自动降级刻意保留 PENDING，却只补了下架动作，没补「人工确认举报成立」这个终态动作。
  3 hideContact 落了处置但漏了撤销路径（同类处置 restore 有、showContact 无）。
  4 队列排序键当时只考虑单类型，未意识到 target_id 跨类型会撞号。
  5/6 申诉写入口比举报写入口少做了一步账号校验与一次唯一键冲突映射。

处理
  A restore 幂等短路（ReviewService.restore）：进方法先判 post.status == APPROVED，是则记
    日志直接返回，不迁移、不写审计。消除「作者申诉后、复审前他人已手工恢复」的窗口，避免
    复审因非法迁移整体回滚。
  B 新增「维持下架」处置（ReviewService.upholdReports + 端点
    POST /api/admin/posts/{postId}/uphold-reports + 审计码 REPORT_UPHOLD）：前置校验帖子必须
    处于 TAKEN_DOWN（否则抛 ILLEGAL_REVIEW_TRANSITION），取该帖全部 PENDING 举报置 UPHELD，
    按结案条数原子回退 report_count（不直接写 0，避免覆盖并发新增）；无待处理举报抛
    REPORT_NOT_FOUND。只结案举报、不动内容状态。
  C 新增「恢复联系方式可见」处置（ReviewService.showContact + 端点
    POST /api/admin/posts/{postId}/show-contact + 审计码 POST_SHOW_CONTACT）：调
    Post.showContact() 把 contactVisibility 改回 VISIBLE，写审计。补上隐藏的撤销路径。
  D 队列游标纳入目标类型（ReportRepository.findQueueAggregates + ReviewQueueService）：排序键
    与 having 增加第四段「目标类型序」，case 表达式 POST=0 / COMMENT=1；游标格式由三段扩为
    四段「举报数:首报毫秒:目标 id:类型序」，首页哨兵类型序取 Integer.MAX_VALUE。新增目标类型
    时 case 表达式与 ReviewQueueService.typeRank 两处都要补档。
  E AppealService.submit 首行加 userService.requireUsableById(appellantId)，与举报同口径。
  F 申诉落库改 saveAndFlush 并捕获 DataIntegrityViolationException → 抛
    BizException(APPEAL_ALREADY_SUBMITTED)（409-006），把并发唯一键冲突映射为 409 而非 500。

过程中撞到的一个坎

R-22 安全响应头加固（CSP / X-Frame-Options / nosniff / Referrer / Permissions）
--------------------------------------------------------------------------------
[2026-10-06]  类型：安全加固  状态：已交付（后端 API + 前端 SPA 构建产物）
来源：R-22 之前的安全质询——「接口是否都带 token、URL 是否暴露 token、逆向能否击穿后端」
      逐项查证后如实列出 6 项残余风险，其中「无 CSP / 无安全响应头」经用户批准先行加固。

现象
  前后端均未下发任何安全响应头：无 Content-Security-Policy，无 X-Frame-Options，
  无 X-Content-Type-Options，无 Referrer-Policy，无 Permissions-Policy。一旦出现 XSS
  注入点，浏览器没有任何第二道防线；页面也可被任意站点以 iframe 嵌套（点击劫持）。

根因
  Spring Security 默认头策略未显式配置；前端为纯静态产物，托管服务器也不发头。

处理（两层，因为后端 API 与前端 SPA 是两套策略）
  A 后端 API 响应（只返回 JSON 与图片，不托管 SPA 页面）
    SecurityConfig.headers：
      Content-Security-Policy: default-src 'none'; base-uri 'none';
                               frame-ancestors 'none'; form-action 'none'
      X-Frame-Options: DENY（CSP 的 frame-ancestors 在旧浏览器不生效，做双保险）
      X-Content-Type-Options: nosniff
      Referrer-Policy: no-referrer
      Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()
    取最严格 'none' 的前提：已查证 src/main/resources/static/ 无 index.html，
    后端不托管任何页面（仅有 StorageWebConfig 的 /uploads/** 资源映射）。若将来改由
    后端直接托管 SPA，必须放宽此策略，否则页面自身的脚本与样式会被自身头拦死。

  B 前端 SPA 页面（由独立静态服务器托管）
    在 vite.config.ts 增加插件 contentSecurityPolicy()，transformIndexHtml + apply: 'build'，
    生产构建时往 index.html 的 head 顶部注入 meta：
      default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
      img-src 'self' data: blob:; font-src 'self'; connect-src 'self';
      base-uri 'none'; object-src 'none'; form-action 'self'
    只在构建期注入：开发期 Vite 以 JS 动态插入 <style> 并建立 HMR WebSocket，与严格策略冲突。
    style-src 保留 'unsafe-inline' 兼容运行时注入的少量 <style>；connect-src 'self' 依据
    「接口默认同源（/api 由反向代理转发）」，若部署为跨域 API 必须补上其 origin。
    img-src 的 data: blob: 当前未被用到（图片恒为 /uploads 同源地址），**经用户裁决保留**，
    留给客户端本地预览（将来用 FileReader / URL.createObjectURL 做上传前预览时必需）——
    不按死配置清理，vite.config.ts 已留注释说明。
    注意：frame-ancestors 写在 <meta> 里会被浏览器忽略，防嵌套需由托管 index.html 的
    服务器补 X-Frame-Options / frame-ancestors 响应头，前端插件覆盖不到。

过程中处理的一个问题
  C（Spring Security 6.5 API 废弃，与项目 -Werror 冲突）
    SecurityConfig 首次编译失败：
      HeadersConfigurer 中的 permissionsPolicy(Customizer<...PermissionsPolicyConfig>)
      已过时, 且标记为待删除  → ERROR: 发现警告, 而且指定了 -Werror
    用 javap -v 逐类比对确认：permissionsPolicy(Customizer) 带 Deprecated 标记，
    非废弃等价 API 为 permissionsPolicyHeader(Customizer)（无标记）。
    处理：改用 .permissionsPolicyHeader(...)。这是编译期 -Werror 门禁（R-17）第二次
    拦下废弃 API 调用，说明门禁有效。javap 需用全路径 $env:JAVA_HOME\bin\javap.exe。

R-15 软删评论残留不可达的 like_record（孤儿点赞行）
--------------------------------------------------------------------------------
[2026-10-06]  类型：后端缺陷（数据卫生）  状态：已解决（方案 1 的收紧版：只在不可撤回的删除路径上清理）

================================================================================
三、经验（跨条目，务必延续）
================================================================================

1. 几何正确 ≠ 视觉正确。验证叠压、遮挡、裁切类问题，不能只读 getBoundingClientRect——
   它返回的是元素矩形，不含绘制顺序与裁剪信息。R-09 因此被连续两轮检查漏过。正确做法：
   elementFromPoint 探测关键点、或做像素采样。

2. jsdom 没有布局引擎，图层、遮挡、溢出这类问题无法用单测覆盖，断言 class 名只是同义反复。
   这类 bug 只能靠浏览器实测兜底，等 P1 接入 Playwright 后应补端到端断言。

3. 改名/重构时，手写 CSS 是盲区。变量改名不会有编译错误，只有浏览器里才看得见。这类重构
   必须配一次浏览器实测（R-03）。

4. 修 bug 先写能复现的失败测试。R-04 是这条的正面样本：先让 useToast.spec.ts 出 2 个失败，
   再改实现，最后全绿。

5. 语义色的对比度要按用途分档。同一个主色，"大面积装饰"和"承载小字号文字"的要求完全不同；
   #2E8B7A 只能用于前者。危险色同理：danger 管「白字填充底」，danger-deep 管「浅色底上的
   文字」。规则已写进 uno.config.ts 注释（R-08、R-11）。

6. 错误提示只能有一个出口。请求错误一律由 http.ts 拦截器弹窗，页面不得内联渲染，否则必然
   重复（R-06）。

7. 不要为展示差异在请求层开洞。R-06 第一版用 errorToast: false 让调用方决定是否弹窗，被
   否决——展示策略应统一在拦截器，调用方只关心成功与失败。

8. 对比度有两类阈值，改一类会牵动另一类。文字对比是 4.5:1、非文本组件（图标、边框、色块
   边界）是 3:1。R-11 为了让未激活徽标的数字达标而调浅其底色，数字从 4.41 升到 4.70，但徽标
   圆本身对白底的对比反而从 1.15 掉到 1.08。量对比度必须同时算「文字/其底色」与「组件/其
   背景」两组，不能只算被点名的那一处。

9. 把 repository.save 全部 mock 掉的单测，测不到任何数据库约束。R-13 的 NOT NULL 冲突在 15 例
   PostServiceTest 里毫无征兆，只有真实 MySQL 的集成测试一跑就炸。凡是「列约束 / 唯一键 /
   外键 / 默认值」相关的行为，必须由 @DataJpaTest 或端到端集成测试兜底，Mockito 单测不能
   算数。

10. 跨前后端的资源路径要单独确认代理。R-14 的 /uploads 不属于 /api，代理规则只覆盖 /api 时
    前端一切正常、只有图片静默 404。新增任何非 /api 前缀的对外路径（静态资源、回调、
    WebSocket），都要同步检查。

11. 门禁要写成「漏写即失败」，不能「漏写即放行」，并且必须反向验证一次。R-16 能溜过去，是
    因为白名单只活在文档里。ModuleBoundaryTest 采用「动态发现模块 + 未登记即只允许依赖
    common」，于是新增模块忘了登记就是构建失败而非静默通过。写完门禁还要故意制造一次违规看
    它是否真红（本项目做法：临时去掉 comment 的 post，确认报 8 处违规）——永远为真的断言等于
    没写。

12. 非文本对比度不达标时，先问「这个元素非画不可吗」。R-18 的未激活圆对白底只有 1.08:1，
    加描边会让未激活态比激活态还重；直接不画，问题连同视觉负担一起消失。但只要它承载信息
    （如进度），就不能按装饰处理，必须正面达标。

13. 无状态令牌（JWT）下，「登录时校验过了」不构成任何保证。R-19 B 项的现场：封禁发生后，
    旧令牌在有效期内（2h）畅通无阻地继续发帖 / 评论 / 点赞 / 上传。凡是账号级禁令（封禁、
    黑名单、降权），都必须在每个写入口重新判定；只读入口可放行以保留浏览能力。同时规则要
    收敛到单一出处（本项目为 UserService.assertUsable），否则「一处收紧、另一处漏」几乎是
    必然。

14. 实体上的计数器不能用读-改-写。R-19 C 项：无 @Version 的 count++ 在并发下必丢更新，单测
    （mock 掉 repository）完全测不出来。正确做法是原子 UPDATE ... SET c = c ± ?。用
    @Modifying 时还要想清持久化上下文：批量更新绕过一级缓存，同一事务内随后再读该行会拿到
    旧值（需要 clearAutomatically），而清除前必须先 flushAutomatically 落定本事务尚未刷出的
    改动（否则 comment.remove() 这类脏数据会被连带丢弃）。

15. 校验「目标存在」不等于校验「目标可访问」。R-19 A 项：评论点赞只查了评论在不在，没查它
    所属帖子是否可见，于是下架帖成了可读写后门。凡是挂在父资源下的子资源（评论之于帖子、
    文件之于帖子），写入口都必须连同父资源的可见性 / 状态一起校验。

16. 一次性凭证要「抢占式消费」，且消费记录的存活期必须覆盖凭证本身的有效期。R-20 J 项：
    emailToken 带 jti，绑定前先 markUsedOnce 占位，占不到即视为重放——抢占式（而非成功后
    再记）才能让并发请求里只有一个进入创建流程；消费记录的 TTL 取 emailTokenTtl，短于此则
    记录先失效、凭证又能被重放。凭证签名只证明「这是本服务签发的」，不证明「没被用过」。

17. 含密钥的本地配置绝不能放在 src/main/resources。R-20 N 项：resources 下的文件会被打进
    target/classes 与产物 jar，application-local.yml（AES key / email pepper / JWT secret）
    因此进了构建产物。改放 qinglan-server/config/ 后由 Spring Boot 默认的 file:./config/
    加载，启动命令不变；换位置后要手工删掉 target 下的陈旧副本，否则它仍在 classpath 上。

18. 限流要放在校验之前，否则绕过成本为零。R-20 H 项：若先校验格式再计数，攻击者拿一批坏
    文件即可无限次请求而不消耗配额。顺序应为「可写状态 → 频次 → 格式」，让非法请求同样
    计入窗口。

19. 一列承载多种语义，前端必然猜错。R-21 A 项：post.review_reason 在下架时存「类型码[: 说明]」、
    驳回时存自由文本，再叠加「恢复后仍残留旧值」，前端用「是否非空」根本分不清三态。判据要
    用显式的状态字段（本项目新增 takenDown 布尔），不能让前端从字符串内容反推状态；同时
    「处罚被撤销」时应在实体上清空当前理由（历史留在只增不改的审计表），否则恢复后的内容会
    一直挂着失效的处罚说明。表现形式不同、语义不同的数据，宁可分开字段，也不要塞进同一列。

20. 全局浮层的 z-index 不能与既有元素撞值。R-21 B 项：举报弹层初版用 z-50，与 sticky 页头
    同值，谁在上面只取决于 DOM 顺序，一次组件搬动就会翻转。应为页面确定一份固定的分层刻度
    （本项目：页头 z-50 < 弹层 z-[900] < 全局提示 z-[1000]）并写进组件注释，而不是各自随手
    挑一个「够大」的数。

21. 集成测试里用 JdbcTemplate 直查，必须先 flush 持久化上下文。R-21 C 项：JPA 把 flush 推迟
    到事务提交，JdbcTemplate 又完全绕过一级缓存，于是读库拿到的是事务开始时的旧值，出现
    「实体已迁移、库里还是旧状态」的假失败。凡在测试内混合「JPA 写 + JdbcTemplate 读」，读之
    前都要显式 entityManager.flush()。这与第 14 条同源——持久化上下文与数据库之间有两层缓存，
    混用工具时最容易踩。

22. CSP 没有「一份通用模板」，要按「这个响应返回什么」分档。R-22：后端只返回 JSON 与图片、
    不托管任何页面，可取最严的 default-src 'none'（被注入的内容连子资源都加载不了）；前端 SPA
    必须放行自身的脚本与样式，只能取 'self'。给 API 套 SPA 策略等于白写，给 SPA 套 'none' 则
    页面直接白屏。写策略前先查清「这个端点到底吐什么」，并把这个前提写进注释——本项目后端
    CSP 的 'none' 就绑定在「后端不托管 SPA」上，将来若改由后端托管页面，必须同步放宽。

23. 安全头能拦住的攻击面与它自身的盲区都要写清楚，别造成「加了头就安全」的错觉。R-22：
    （a）frame-ancestors 写在 <meta> 里会被浏览器直接忽略，防 iframe 嵌套必须由托管页面
    的服务器发响应头，前端构建插件覆盖不到——只在构建产物里加 meta 不等于防住了点击劫持；
    （b）安全头只是纵深防御的第二道墙，第一位的仍是「不产生 XSS 注入点」（本项目全程无
    v-html、无 innerHTML 拼用户输入），头不能替代输出编码。
    另外：头部类改动必须浏览器实测。响应头存在与否、CSP 有无违规（Refused to load/execute/
    apply style）只有真实浏览器能暴露，MockMvc 只能断言「头被写出来了」，断言不了「页面
    在策略下仍能正常工作」。

24. -Werror 门禁的真实价值在「拦住后来废弃的 API」，而不只是拦住新写的坏代码。R-22 C 项：
    SecurityConfig 用了 Spring Security 6.5 已标记 @Deprecated 的 permissionsPolicy(Customizer)，
    编译期直接红。判断「哪个是替代 API」不能靠猜，用 javap -v 比对两个候选成员的 Deprecated
    标记最可靠（本项目据此确认应改用 permissionsPolicyHeader(Customizer)）。这是 R-17 立的
    编译门禁第二次拦下废弃调用，与第 11 条同理——门禁要常驻，且要真的能红。

25. 「已经是目标态」不等于「非法迁移」，幂等入口要先短路。R-23 A 项：restore 只考虑了
    TakenDown → Approved，当帖子已被他人手工恢复成 Approved 时，复审再走一次 Approved →
    Approved 会被状态机判非法并整体回滚，连带把申诉状态也退回。凡是从外部可重复触发的状态
    迁移（复审、重试、回调），入口都要先判「是否已经是目标态」，是则直接返回，而不是硬闯
    状态机。判据要用显式的状态字段，不要从别的字段反推（与第 19 条同源）。

26. 「系统先动手、人后确认」的流程，必须把人工终态动作单独做出来。R-23 B 项：举报数达阈值
    自动下架时举报刻意保持 PENDING 好留在队列，但只做了自动下架、没做「人工确认举报成立」，
    于是管理员要么走首次下架（对已下架内容非法），要么走驳回举报（语义是「内容不违规」），
    举报永远清不掉。补动作时语义不能与相邻动作混淆（「维持下架」≠「驳回举报」）——相邻动作
    名字相近但语义相反时，最容易漏掉其中一个。

27. 排序键与游标必须覆盖「全部可能撞号的列」。R-23 D 项：target_id 只在各自类型内唯一，帖子
    #7 与评论 #7 会撞号；只按 reportCount/firstReportedAt/targetId 三键分页，两键并列时无法
    区分，翻页会漏行或重复。复合游标要包含能把每行唯一确定的全部列，且 having 的比较顺序
    必须与 order by 严格一致。另：JPQL 里 case ... then 0 else 1 end 的 0/1 字面量被 Hibernate
    推断为 Integer，对应参数必须声明 int——声明成 long 时首页哨兵 Long.MAX_VALUE 会在绑定
    参数处直接抛 InvalidDataAccessApiUsage（表现为接口 500），而单测用 mock 完全看不出来。

28. 同一个「写入口家族」（举报 / 申诉 / 评论…）的校验步骤要对齐。R-23 E/F 项：申诉比举报少了
    requireUsableById（封禁账号仍可申诉）与唯一键冲突的 409 映射（并发重复提交抛 500）。多个
    写入口做同类事情时，把公共校验抽到一处、或至少维护一份 checklist，否则「一处收紧、另一处
    漏」几乎必然发生（与第 13 条同源）。约定好的错误码（如重复提交 409）必须显式捕获约束
    异常去映射，不能指望全局兜底自动给出正确的状态码。

29. 验证脚本自己的错报，比产品缺陷更容易骗过自己。R-24 的接口级端到端脚本在调用
    POST /api/admin/posts/{id}/approve 时返回了空状态（无 statusCode、无响应体），我据此写下
    「审核未生效」；实际该接口 18ms 就返回 200、库里状态已变、通知也已发出——问题出在脚本
    用的 mysql 客户端把密码警告写到 stderr，而 PowerShell 5.1 在 ErrorActionPreference=Stop 下
    会把原生命令的 stderr 当成致命错误。教训有两条：探针报出「奇怪的状态码」时，先用另一条
    通道（直连接口、查库）交叉确认，再下结论；原生命令不要用 -p<密码>，改用环境变量传凭据。

30. 「改的是全局组件」这件事必须显式检查。R-24 把 AppHeader 的容器宽度写死成 1200px，而它作用
    于全部学生端页面，于是 4 个内容仍为 720px 的页面头部与内容左边缘错开 232px。当时的实现计划
    里还写着「其余 4 个页面零改动」——文件确实没改，但视觉效果被改了。改 props、容器类、全局
    样式这类横向影响面时，先列出受影响页面清单，并让「头部的容器宽度」与「内容的容器宽度」
    由同一个判断驱动，而不是各自决定。

31. 不要在同一轮里让两个子代理改同一个文件。R-24 的 T5 与 T6 都被要求往 App.vue 接线，结果
    并发提交把对方的 import 顶掉过，虽然最终补齐且测试全绿，但合并后的文件没经过逐行审查、
    提交归属也乱了。并行拆分必须以「文件零重叠」为准，公共入口文件只交给一个执行者。

32. EXPLAIN 的结论依赖数据量。R-24 对三张刚刚建好的空表跑 EXPLAIN，优化器给出的 rows 全是 1、
    选中的索引带有随机性（通知列表本可走 (user_id, id) 免排序，实际却选了另一个索引并产生
    filesort）。空表上的 EXPLAIN 只能证明「索引存在且可被选中」，不能证明「生产规模下是最优
    计划」。这条结论要么在造数后重跑，要么在文档里标明局限，不要当成功效验证。

33. 全局提示的层级必须高于第三方组件库的弹层。Element Plus 的 defaultInitialZIndex 是 2000 且
    每开一个弹层递增，而我们自己的层级注释只写到 1000——于是「管理端弹窗内请求失败」的提示被
    遮罩压在下面：看不见也点不掉，而按第七章的错误唯一出口约定页面又不会内联渲染它。引入第三方
    弹层时，先查它的默认层级常量，再把全站 z 轴口径写成一处唯一来源（本项目在 uno.config.ts 的
    theme.zIndex），不要散落在各组件里靠注释约定。

34. 自定义 UnoCSS 主题键必须核对构建产物。theme.zIndex 加了键之后，z-toast 这类类名到底有没有
    被生成，dev 与单测都看不出来——不生成就是静默失效，比写错颜色更难发现。改完先 build + 在
    dist 的 CSS 里 grep 一次，再往下做。同理适用于任何新增的 theme 键（spacing、breakpoint 等）。

35. 事件的 .stop 与 .prevent 不能互相替代。stopPropagation 只拦监听器，不阻止浏览器的默认行为；
    锚点 (<a>) 内的按钮两种都要：.stop 让 Vue Router 的 guardEvent 拿不到事件（不 push），
    .prevent 取消 <a> 的默认跳转，否则用户仍会被带去做整页导航。

36. 修好行为不等于消除结构缺陷。`<button>` 嵌在 `<a>` 里用 `.prevent.stop` 能修正行为，但结构
    依然非法、语义依然混乱；重构结构往往有代价（本次是可点区域缩小）。这类取舍要显式权衡，
    并把「只修了行为」记进待办，不要让后来者以为它已经干净了。

37. 测试断言实现细节会反过来锁死规范。BaseCard.spec 断言 `sm:p-6`，于是把 `sm:` 改写成
    `max-sm:`（AGENTS.md 第七章）必须先改测试——这正是 T-19 拖了一轮的真实原因（当时的备注写的是
    「怕影响既有断言」，没写清是这条）。断言应落在结构或行为上（如「基线 + 收窄」这层关系），
    而不是某个具体的原子类名或列下标。

38. jsdom 不实现 label 的激活行为。R-25 里「点分组标题把单选值改掉」这类由 HTML 规范决定的缺陷，
    没法用 click 在单测里复现（点了不会激活控件）。可行的办法是断言**结构**（radio 的祖先里不能
    再有第二个 label），并在注释里写清为什么用结构断言、以及为什么不能用行为断言。

39. 同一份「登录态」不能有两个来源。R-26 的根因是 store 的内存态与请求头的持久化态各写一半：
    存储不可用时二者分歧，表现为「已登录却全 401」。修法是把唯一权威放内存、持久化只做跨刷新
    兜底，并把读写收进 api/http 的一对函数——凡是需要跨模块共享的状态，都要先回答「谁是权威」。
    副作用：模块级状态不会在测试间自动复位，凡依赖它的 spec 必须在 beforeEach 里显式清零
    （R-26 里 useNotifications.spec 因此补了 setAuthToken(null)），否则「已登录」用例会漏进
    「未登录」用例。

40. 断言要断到「语义那一层」。整段文本 toContain('2')、toBeTruthy 这类零头断言，在日期时间或
    任意非空值面前都会「恰好通过」，等于没测。R-26 把它们改成「举报数单元格文本恰为 2」「deviceId
    匹配 UUID」。判断标准：撤掉被测逻辑后断言是否还会通过——会通过就说明断错了层。
